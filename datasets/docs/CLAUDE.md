# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A from-scratch Text-to-SQL Transformer LLM. Natural-language questions are converted to SQL
(e.g. `how many mouse units are left in stock ?` → `SELECT stock FROM items WHERE item_name = 'mouse';`).
The project starts with a narrow SQL scope (single table, single WHERE equality condition) and expands
in stages. Full plan, rationale, and design decisions are in
[text-to-sql-llm-project-plan.md](text-to-sql-llm-project-plan.md) (Korean) — read it before making
architectural changes, since most "why" decisions live there, not in code comments. For a per-function
input/output reference across `db/db_gen.py`, `db/sql_gen.py`, `db/question_gen.py`, `bpe_tokenizer.py`,
and `dataset.py`, see [function-reference.md](function-reference.md) (Korean).

### Directory layout

This repo's actual root is `capstone-design-1/` (shared with the other 3 teammates). Everything 팀원1 owns —
code, data, and this doc set — lives under `capstone-design-1/datasets/`, isolated from teammates' folders. This
file and its sibling docs sit one level further down, in `capstone-design-1/datasets/docs/`. So when a command
below says "repo root," it means `datasets/`, not the actual git root — and links from this file to code
(`db/`, `bpe_tokenizer.py`, `dataset.py`) go up one level (`../`) to reach them, while links to sibling
docs (`SETUP.md`, `function-reference.md`, etc.) stay in the same folder.

### Scratch-build constraint (critical, do not violate)

The model, tokenizer, training loop, and inference must be implemented from scratch. This is the point
of the project, not an implementation detail.

| | Allowed | Forbidden |
|---|---|---|
| Libraries | Python stdlib, PyTorch (tensor ops/autograd/optimizer only), SQLite, NumPy, TensorBoard | HuggingFace `tokenizers`/`transformers`, SentencePiece, tiktoken, or any other complete off-the-shelf model/tokenizer |
| Weights | Random init only | Pretrained checkpoints |
| Data | DB/SQL generated by Python code; NL questions generated by an external LLM; some eval questions hand-written | LLM must never generate or modify the ground-truth SQL — SQL correctness is always decided by code |
| Reference | nanoGPT may be read and adapted/rewritten | — |

When adding dependencies or writing model/tokenizer/training code, respect this table.

## Commands

The three generators live in [db/](../db/) and write to `db/data/` by default; run them from inside `db/`
(i.e. `datasets/db/`). `bpe_tokenizer.py` lives in `datasets/` (see Directory layout above — not the
actual repo root) and reads `db/data/...` as a relative path, so run it from `datasets/` instead. See

```
cd datasets/db          # from the repo root (capstone-design-1/)
python db_gen.py build      # generate db/data/shop.db and db/data/holdout.json

python db_gen.py test       # 4 checks: distribution, determinism, price equality, holdout separation
python db_gen.py summary    # print row counts and value distributions
python db_gen.py space      # compute the count of unique SQL queries the stage-1 grammar can produce
```

(default 0), `--out DIR` (default `./data`), `--name-style single|two_word` (default `single`).

```
python sql_gen.py build --cap-nonid 9999 --cap-id 9999   # db/data/sql_train.json, db/data/sql_eval_indist.json
python sql_gen.py verify                                  # re-check the 3 completion conditions (3-3 step 2)
python sql_gen.py test                                    # determinism, no holdout literals, train/eval disjoint
python sql_gen.py summary                                 # per-(table, where_col) quota table
```

## DB generator architecture ([db/db_gen.py](../db/db_gen.py))

Generates a fixed-schema SQLite shop DB: `customers` (300 rows) — `items` (200 rows) — `orders` (500 rows,
N:M bridge). Design choices that affect any code built on top of this DB:

- **Single-word names**: `customers.name` and `items.item_name` are single words drawn from fixed pools
  (`GIVEN_NAMES`, `CATEGORY_NOUNS`), to keep token counts low for the stage-1 model. `--name-style two_word`
  regenerates with two-word names for later stages.
- **Separate ID ranges per table** (customers 1000s, items 3000s, orders 5000s) reduce accidental
  cross-table result collisions during execution-accuracy evaluation, but create a shortcut (guessing table
  from ID's leading digit) — `sql_gen.py` counters this via `id_nonexistent_ratio` (default 20%), filling
  part of the ID-condition quota with IDs that don't exist (0-row results).
- **Holdout separation** (`build_holdout`/`load_bans`): a portion of rows/IDs are held out into
  `data/holdout.json` in three tiers — unseen entity (name + ID both unseen), unseen-ID-only (name seen,
  ID unseen), unseen order ID. `sql_gen.py` reads this file (`db_gen.load_bans`) and excludes these
  literals from training SQL, so they can be used to measure generalization to unseen values.
- **Determinism**: `canonical_hash()` hashes row *content* (not the `.db` file bytes) so equality checks
  survive incidental SQLite file differences; same seed must always reproduce identical rows.
- **Balanced sampling** (`balanced_column`): categorical columns (city, membership, category, status,
  quantity) are sampled with per-value minimums (and, for item category, capacity caps from the noun
  pools) so no category is starved — required because the downstream SQL generator stratifies by
  (table × SELECT column × WHERE column) rather than sampling uniformly (uniform sampling would make ~65%
  of generated SQL be `WHERE *_id = <number>`, since ID columns have far more distinct literals than
  categorical ones).
- All text values are stored lowercase; SQL keywords are expected uppercase in generated SQL (normalization
  rules, plan section 4-3).

## LLM question-generation pipeline architecture ([db/question_gen.py](../db/question_gen.py))

Turns `sql_gen.py`'s SQL into (question, SQL) training pairs. LLM output is never trusted as ground truth —
`validate()` always re-checks it in code (literal-value inclusion, lowercase, no spelled-out numbers, no
known synonym swaps) before a pair is accepted, per the scratch-build constraint in the table above.

- **Round-based, not one-shot**: each run samples `--n` not-yet-used SQL into a new `data/pilotN/` directory
  (`--exclude-dir` lists every prior round so SQL is never reused across rounds), producing one prompt file
  per 25-SQL batch. Rounds accumulate toward the full training corpus rather than being redone from scratch.
- **One independent LLM session per batch, not one session per round**: this was the single biggest lever
  found for output diversity, and it was not obvious in advance. A single session (human or agent) asked to
  write questions for many SQL rows that share the same `(SELECT column, WHERE column)` shape converges onto
  a small set of go-to phrasings once it recurs more than roughly 10-12 times — this happened regardless of
  round size (200 vs 500), regardless of whether the session used a script, and regardless of how strongly it
  was told to vary its phrasing. Splitting a round's batches across separate independent agent sessions (or
  mixing in genuinely separate human sessions) fixed it: comparable rounds went from ~70-80% repeated
  "skeletons" (same session, whole round) down to ~17-22% (one independent session per 25-SQL batch).
  Do not process an entire round's batches in one session again.
- **Do not let the generating session write a generator script**: a session asked to fill hundreds of
  entries will sometimes reach for a phrase-bank/template script "for efficiency" (or even specifically to
  defeat `template_check`'s duplicate-skeleton metric by permuting noun-phrase pools) instead of composing
  each question. This produced either ungrammatical output (mechanically concatenated noun phrases) or a
  reused invented phrase repeated verbatim across dozens of entries — both undetectable by the skeleton-based
  diversity check, only found by reading actual sentences. Instruct against this explicitly and spot-check
  the literal text, not just the automated pass rate.
- **`validate()`'s hard checks are gameable, and were gamed more than once**: 100% pass rate proves the rules
  were followed, not that the language is natural or diverse. A session that already knows (or infers) the
  checker's exact rules can satisfy them with minimum effort. Where possible, keep the checker's internals
  out of the generating session's context, and always eyeball a sample of the real sentences.
- **`template_check()` catches gross repetition, not everything**: it flags `(SELECT col, WHERE col)` shapes
  where many entries share an identical skeleton (question text with the literal value masked out). It
  correctly identifies whole-session convergence and lazy exact-copy templating, but a sufficiently engineered
  combinatorial phrase-pool can drive its ratio to 0% while still producing unnatural, repeated fixed noun
  phrases (e.g. inventing "the item's category label" and reusing that exact string everywhere) — treat a
  suspiciously perfect 0% as a reason to inspect the text, not a pass.
- **A round's data doesn't need to be discarded for being repetitive**: a (question, SQL) pair with a
  reused phrasing is still a correct pair, just a less diverse one. `pass_rate`/`template_check` decide
  whether a round's *generation method* needs fixing before scaling it up further, not whether that round's
  already-produced pairs get thrown away.

## BPE tokenizer architecture ([bpe_tokenizer.py](../bpe_tokenizer.py))

A from-scratch byte-level BPE tokenizer (no HuggingFace `tokenizers`/SentencePiece/tiktoken, per the
scratch-build constraint above). Vocab size is fixed at 1,024, laid out in four contiguous ID ranges:

| ID range | Count | Content |
|---|---|---|
| 0–255 | 256 | raw UTF-8 byte values (byte-level base — guarantees no OOV, every string is encodable) |
| 256–259 | 4 | special tokens `<pad> <bos> <eos> <sep>` |
| 260–297 | 38 | seed tokens — SQL keywords, column names, category/city/status values (whole-string, never split) |
| 298–1023 | 726 | corpus-frequency BPE merges (`MERGE_BASE = SEED_BASE + len(SEED_TOKENS)`, computed, not hardcoded) |

- **Seed tokens are a deliberate vocab-budget decision**: domain-closed vocabulary (`WHERE`, `item_id`,
  `electronics`, city names, etc.) is pinned to one token each up front, so the 726-merge budget is spent
  on names, numbers, and question wording instead of re-deriving fixed SQL/schema vocabulary from bytes
  every time.
- **Regex-based pre-tokenizer** (`_build_pattern` / `pre_tokenize`): seed tokens are matched first
  (longest-first, `\b`-bounded, so `"new york"` isn't shadowed by a shorter alternative) and never split;
  everything else falls through to alphabetic runs, single digits, whitespace, and a catch-all. `pre_tokenize`
  asserts there are no gaps, and `check_roundtrip()` asserts the pieces reassemble the original string
  exactly — enforced at call time, not just checked after the fact.
- **Deterministic merge selection**: on a tie in pair frequency, `train()` always picks the pair with the
  lexicographically smallest `(id, id)` tuple, so the same corpus always produces the same 726 merges in the
  same order regardless of dict iteration order or hash randomization.
- **Training corpus** (`load_corpus()`): glob `db/data/pilot*/pilot_train_pairs.json` — matches
  `db/data/pilot_merged/` (23,045 pairs × 2 strings = 46,090; the 13 raw `pilot`..`pilot13` rounds it was
  consolidated from now live outside the glob path, in `db/data_raw/` — see Current state above), **not**
  `eval_indist_merged` (different name prefix, doesn't match `pilot*`). This means the in-distribution eval
  set never influenced the learned merges — a deliberate-looking side effect of the glob, not stated as
  intentional anywhere, but worth preserving: don't widen this glob to include eval data without
  considering that it'd leak eval strings into vocab training.
- **Verified** (by running `python bpe_tokenizer.py`): 726/726 merge budget used, exact round-trip on all
  46,090 corpus strings (0 failures), and 3.49 average subword tokens per name on the holdout unseen-entity
  pool (60 customers + 40 items) — under the plan's 4-token threshold (5-2). Since the corpus and tie-break
  rule are both fixed, this run is fully reproducible: rerunning produces byte-identical `bpe_merges.json`.

## Dataset architecture ([dataset.py](../dataset.py))

Turns tokenized (question, SQL) pairs into PyTorch batches. Two design decisions here aren't obvious from
the code alone:

- **Sequence format**: `<bos> question <sep> sql <eos>`, built by `encode_pair()`. `tokenize_pairs()` also
  records `sql_start` (the index right after `<sep>`) on each example, since it's needed by both the loss
  mask and the round-trip checks.
- **Loss is computed on the SQL side only, never on `<bos>`/question/`<sep>`**: at inference time the model
  never has to generate the question (it's given), and this project's training data has 5 differently
  phrased questions per SQL — training the model to also predict question tokens would spend the limited
  gradient signal on high-entropy, non-target text instead of the actual task, which matters more here than
  usual given the plan's own "~9 params/token, memorization-heavy" concern (see plan section 2). `collate_fn`
  builds this as a `loss_mask` that's `True` only for target positions from `sql_start` onward (i.e. every
  SQL token plus the final `<eos>`) and `False` everywhere else, including padding.
- **Padding is dynamic per batch, not fixed to the context length (128)**: `collate_fn` right-pads each
  batch only to that batch's own max length. Measured sequence lengths across all 28,815 train+eval_indist
  pairs are 23–64 tokens (mean 38.2, p99 52) — padding every batch out to a fixed 128 would waste roughly
  2–3x the compute for no benefit. Padding is on the right because this is a causal (unidirectional) decoder:
  a real token at position *i* only ever attends to positions ≤ *i*, so it can never see trailing padding
  regardless of whether an explicit attention/padding mask is added — the `loss_mask` alone is enough to keep
  padding out of training signal.
- **Verified** (by running `python dataset.py`): 0/28,815 sequences exceed context length 128; sample
  round-trips (`bpe.decode` reconstructing the original question/SQL from token IDs) all pass; `collate_fn`'s
  `loss_mask` true-count matches the expected SQL+`<eos>` length on every checked row.

## Data generation stage plan

The project proceeds in stages that each widen SQL scope and re-train a fresh tokenizer/model (vocab and
context length change per stage, so nothing is fine-tuned across stages — see plan 3-3):

1. **(current)** `SELECT` single column or `*`, `WHERE` single equality, 3 fixed tables, no JOIN
2. Add multi-condition `WHERE` (AND/OR), comparison operators, `ORDER BY`, `LIMIT`
3. Add `GROUP BY`/`HAVING`/aggregates, single-level subqueries
4. Add 2-table JOIN (schema expands to 5–10 tables)
5. (stretch) multi-JOIN, nested subqueries

Each stage's output must include separate held-out-value and held-out-structure evaluation sets — see plan
section 3-5 for the exact metrics (Exact Match primary, execution accuracy secondary) and the stage-gate
thresholds.

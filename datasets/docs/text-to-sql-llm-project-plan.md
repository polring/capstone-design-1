# Text-to-SQL LLM 스크래치 빌드 프로젝트 계획서

## 1. 개요

### 1-1. 목표
- 자연어 질의를 SQL로 변환하는 Transformer 언어모델을 **직접 구현하여 처음부터 학습**한다.
  - 예: `how many mouse units are left in stock ?` → `SELECT stock FROM items WHERE item_name = 'mouse';`
- 좁은 범위(단일 테이블, WHERE 단일 조건)에서 정확도를 먼저 확보하고, 단계적으로 SQL 범위를 넓힌다.

### 1-2. 스크래치 원칙
스크래치로 구현하는 범위는 **모델·토크나이저·학습·추론**이다. 데이터 생성에는 외부 LLM을 활용하되, **SQL 정답은 항상 코드가 결정**한다.

| 구분 | 허용 | 금지 |
|---|---|---|
| 라이브러리 | Python 표준 라이브러리, PyTorch(텐서 연산·autograd·옵티마이저), SQLite, NumPy, TensorBoard | HuggingFace tokenizers/transformers, SentencePiece, tiktoken 등 완성품 |
| 가중치 | 무작위 초기화 | 사전학습 체크포인트 |
| 데이터 | DB·SQL은 Python 코드로 생성, 자연어 질문은 외부 LLM으로 생성, 평가용 질문 일부는 사람이 직접 작성 | LLM이 SQL 정답을 만들거나 수정하는 것 |
| 참고 코드 | nanoGPT를 읽고 참고하여 재작성 | — |

### 1-3. 구현 구성 요소
1. DB 생성기
2. SQL 생성기
3. LLM 질문 생성 파이프라인 (배치 구성·호출·자동 검증)
4. BPE 토크나이저
5. Decoder-only Transformer 및 학습 루프
6. 제약 디코더 및 평가기

### 1-4. 하드웨어
- 주력: RTX 4070 Super (12GB VRAM)
- 보조: Colab 무료 GPU (세션 시간·GPU 종류가 보장되지 않으므로 보조 실험용)

### 1-5. 관련 문서
본 문서는 전체 방향과 단계별 진행 계획을 다룬다. 데이터 제작(값 풀, LLM 프롬프트, 검증, 데이터 분할), 토크나이저, 모델·학습 설정, 평가 설계의 상세 내용은 별도 문서로 작성한다.

## 2. 제약 조건

| 항목 | GPT-3 / Llama 2 7B | 본 프로젝트 1단계 |
|---|---|---|
| 파라미터 수 | 70억 ~ 1,750억 | 약 502만 (5.02M) |
| 학습 토큰 수 | 3,000억 ~ 2조 | 약 1,400만 (고유 약 56만 × 약 25 epoch) |
| Vocab 크기 | 32,000 ~ 약 50,000 | 1,024 |
| 컨텍스트 길이 | 2,048 ~ 4,096 | 128 |
| 데이터 | 웹 규모 코퍼스 | SQL 4,000개 × 질문 5개 = 학습 2만 쌍 |
| 처리 범위 | 임의의 자연어/SQL | 고정 스키마, 단일 테이블, WHERE 단일 등호 조건 |

- 대규모 사전학습이 불가능하므로 **고정 스키마 전용 파서(specialist)** 로 설계한다.
- 이 규모에서는 모델 크기보다 **질문 표현의 다양성, 값의 다양성, SQL 구조의 커버리지**가 성능을 좌우한다. 따라서 로드맵에서 모델 크기는 완만하게 늘리고, 단계마다 데이터 설계에 무게를 둔다.
- 컨텍스트 128은 간이 프로토타입(5장 스키마 기준)에서 측정한 질문+SQL 길이(평균 28, 최대 38토큰)에, LLM 대화체 문장과 사람 작성 질문의 길이 여유를 더한 값이다. **실측 완료(2026-09-21)**: `dataset.py`가 `<bos> question <sep> sql <eos>` 형식으로 전체 학습+분포 내 평가 28,815쌍을 토큰화한 결과 평균 38.2, 최대 64, p99 52토큰으로 나왔다 — 프로토타입 추정치보다 길었지만(특수 토큰 4개 추가와 `<sep>` 포맷이 반영된 값이라 그렇다), 128에는 여전히 여유 있게 들어간다(초과 0/28,815). 컨텍스트 128은 그대로 유지한다.
- **1단계는 데이터 대비 모델이 크다.** 고유 학습 토큰 56만에 파라미터 502만으로, 토큰당 파라미터가 약 9개다. 사실상 암기가 일어나는 영역이며 이는 "미등장 값" 성능을 직접 깎는다. 1단계 ablation에서 모델 축소(4층·192차원, 약 2M)와 질문 수 증가를 함께 비교한다.

## 3. 단계별 진행 계획

### 3-1. 단계별 SQL 범위

| 단계 | 추가되는 SQL 범위 | 스키마 |
|---|---|---|
| **1 (현재)** | SELECT 단일 컬럼 또는 `*`, WHERE 단일 등호 조건 | 3개 테이블 고정, JOIN 없음 |
| 2 | WHERE 2~3개 조건(AND/OR), `> < >= <= != BETWEEN`, ORDER BY, LIMIT | 동일 |
| 3 | GROUP BY, HAVING, COUNT/AVG/SUM/MIN/MAX, 1단계 서브쿼리 | 동일 |
| 4 | 2테이블 JOIN | 테이블 5~10개로 확장 |
| 상한 | 다중 JOIN, 중첩 서브쿼리 | 학습된 스키마 한정 |

### 3-2. 단계별 자원 계획

| 단계 | 구조 (층/차원/헤드) | 파라미터 | Vocab | 컨텍스트 | 학습 데이터 (SQL × 5문장) | LLM 호출¹ | 학습 토큰² | 추정 학습 시간³ |
|---|---|---|---|---|---|---|---|---|
| **1** | 6 / 256 / 4 | 5.02M | 1,024 | 128 | 4,000 × 5 = 2만 | 약 200회 | 1,400만 | 수 분 |
| 2 | 8 / 384 / 6 | 15.0M | 2,048 | 128 | 4만 × 5 = 20만 | 약 1,600회 | 9,000만 | 9~14분 |
| 3 | 8 / 512 / 8 | 27.4M | 4,096 | 256 | 8만 × 5 = 40만 | 약 3,200회 | 2.8억 | 53~80분 |
| 4 | 12 / 512 / 8 | 42.2M | 8,192 | 512 | 20만 × 5 = 100만 | 약 8,000회 | 10억 | 5~7.6시간 |
| 상한 | 12 / 768 / 12 | 91.6M | 8,192 | 512 | 30만 × 5 = 150만 | 약 12,000회 | 20억 | 21~32시간 |

¹ 요청 1회에 SQL 25개 기준. 1단계는 분포 내 평가용 SQL 1,000개 생성분을 포함한다(총 5,000개 ÷ 25 = 200회).

² 학습 쌍 수 × 쌍당 평균 토큰 × epoch. 쌍당 평균 토큰은 1단계 28(프로토타입 측정), 2단계 45, 3단계 70, 4단계 100, 상한 130으로 가정했다. epoch은 1단계 25회, 이후 10회다. 데이터 생성 후 실측값으로 교체한다.

³ 1회 학습 기준이다. 산출 근거와 실측 보정 방법은 3-4에 있다. ablation과 반복 실험을 고려하면 실제 소요 시간은 3~5배로 잡는다.

- **메모리**: AdamW 학습에는 파라미터당 약 16바이트(가중치·그래디언트·옵티마이저 상태)가 든다. 상한 단계(91.6M)도 약 1.5GB에 activation을 더한 수준이므로, 모든 단계를 12GB 안에서 학습할 수 있다.
- **헤드당 차원**은 모든 단계에서 64로 통일했다.
- **학습 종료**: 표의 epoch은 상한값이며, 실제로는 검증셋 정확도가 더 오르지 않으면 조기 종료한다.
- **비용**: 이 표에 GPU 시간은 있으나 LLM API 비용과 사람 작업 시간은 빠져 있다. 3단계 이후 실제 병목은 이쪽이므로 별도 문서에서 추정한다.

### 3-3. 단계별 진행 방식

#### 공통 진행 사이클
각 단계는 아래 순서로 진행한다.

1. **SQL 생성기 확장**: 해당 단계의 SQL 구조 조합을 코드로 빠짐없이 열거하고, 구조별 할당량을 정해 층화 샘플링한다.
2. **평가 질문 준비**: 사람이 쓰는 평가 질문을 LLM 생성보다 **먼저** 작성해 봉인한다. LLM 문장을 먼저 보면 그 말투를 따라 쓰게 되기 때문이다.
3. **파일럿**: SQL 200개(질문 1,000개)만 생성해 검증 통과율과 표현 다양성을 확인하고, 학습·평가까지 한 번 끝까지 돌려 본다. (1단계에서 확인된 방법론: 질문 생성은 **배치 하나(SQL 25개)당 서로 독립된 LLM 세션 하나**에게 맡긴다. 세션 하나가 라운드 전체를 처리하면 같은 (SELECT 컬럼, WHERE 컬럼) 조합이 10여 개를 넘는 순간 표현이 소수의 "무난한 문장"으로 수렴한다 — 라운드 크기를 줄여도, 스크립트 작성을 금지해도 이 현상 자체는 안 없어졌고, 배치를 독립된 세션으로 쪼개는 것만 효과가 있었다. 자동 검증 통과율은 규칙 준수만 보장하므로, 실제 문장 표본을 사람이 직접 읽어 확인하는 절차를 병행한다.)
4. **전체 데이터 생성**: 파일럿으로 확정한 프롬프트로 일괄 생성하고 자동 검증을 거친다.
5. **학습**: 토크나이저와 모델을 해당 단계 설정으로 **새로 학습**한다. vocab과 구조가 단계마다 바뀌기 때문이다. 이전 단계 유형의 SQL도 학습 데이터에 20~30% 섞어 기존 능력을 유지한다.
6. **평가 및 게이트 판정**: 3-5 기준을 통과하면 다음 단계로 넘어간다. 통과하지 못하면 데이터를 보강한 뒤 4~6을 반복한다.

#### 단계별 핵심 과제

| 단계 | 핵심 과제 | 주요 점검 사항 |
|---|---|---|
| **1** | 전체 파이프라인(1-3의 6개 구성 요소)을 처음 구축하고 동작을 검증한다 | 처음 보는 값(이름·ID)을 질문에서 정확히 복사하는가, 사람이 쓴 질문에도 동작하는가 |
| 2 | 조건 개수 × 연산자 × AND/OR × ORDER BY 유무 × LIMIT 유무 조합을 체계적으로 생성한다 | 일부 구조 조합을 학습에서 빼 두고, 처음 보는 조합에 대한 일반화를 따로 측정한다 |
| 3 | 집계·그룹화 SQL의 표기 규칙을 통일한다 (예: `COUNT(*)`로 고정) | 의미는 같은데 형태가 다른 SQL이 늘어나므로 실행 결과 비교의 비중을 높인다. 주문 데이터(500행)로 집계 결과(예: 상품별 주문 수량 합계, 카테고리별 재고 합계)가 의미 있게 나오는지 확인한다 |
| 4 | 스키마를 확장하고 join 경로를 커버한다 | 스키마가 고정돼 있으므로 모델은 FK 관계를 추론하기보다 join 경로를 **암기**한다. 따라서 모든 join 경로가 학습 데이터에 충분히 나오는지가 관건이다. 1~3단계에서 불가능했던 "고객 이름으로 주문한 상품 조회" 같은 질문이 가능해진다 |
| 상한 | 4단계 결과를 보고 진행 여부를 결정한다 | 중첩 구조는 데이터 생성 비용이 급증하므로 비용 대비 효과를 먼저 판단한다 |

#### 진행 기록 — 계획과 실제의 차이 (2026-09-19)

- **LLM 질문 생성이 계획보다 빨리 끝났지만, 순서는 계획과 달랐다.** 원래 사이클은 "3번(사람 작성 질문 봉인) → 4번(파일럿) → 전체 생성"이었으나, 실제로는 3번을 건너뛴 채 파일럿을 13라운드까지 누적해 학습용 23,045쌍(목표 100%)을 먼저 완성했다. `validate()` 통과율은 전 라운드 100%. `template_check` 반복 비율은 초반(pilot~pilot5) 32~77%로 높았다가, "배치당 독립 세션" 방식이 정착된 pilot6 이후 15~20%대로 안정됐다. 예외로 pilot13(55쌍)만 반복 비율 0%였으나, 55개 전량 육안 확인 결과 매번 실제로 다른 단어를 써서 나온 정상적인 다양성이었다 — 다만 그룹(SQL 1개당 5문장)마다 격식체·캐주얼체·키워드체 등 같은 순서의 "말투 로테이션"을 반복하는 상위 패턴은 있었다.
- **"파일럿"과 "전체 데이터 생성"이 사실상 하나의 과정으로 합쳐졌다.** 공통 진행 사이클(3-3 상단)은 파일럿(SQL 200개) 이후 별도의 "전체 데이터 생성" 라운드를 상정했지만, 실제로는 같은 파일럿 절차를 13번 반복해 목표치를 채웠다. `question_gen.py`의 라운드 누적·`--exclude-dir` 구조가 이 방식에 그대로 맞아 문제는 없었지만, 계획서의 2단계 구분과는 다르게 진행됐다.
- **평가용 SQL에는 아직 질문이 없다.** `sql_gen.py build`가 만든 `sql_eval_indist.json`(분포 내 평가용 SQL 1,154개)은 처음부터 존재했지만, `question_gen.py`는 지금까지 전량 `sql_train.json`(학습용)만 입력으로 사용했다. 3-5의 "분포 내" 평가를 계획대로 하려면 이 파일에도 같은 파이프라인(질문 생성 → 검증)을 최소 한 번 더 돌려야 한다.
- **의사결정 (2026-09-19)**: 사람 작성 평가 질문(3번)과 분포 내 평가용 질문 생성(7번 잔여분)은 일단 보류하고, 토크나이저 구현(5번)을 먼저 진행하기로 함. 토크나이저부터는 학습 목적상 직접 구현. 사람 작성 질문을 나중에 쓴다면, 이미 13라운드의 LLM 문장에 노출된 뒤이므로 "봉인 후 작성" 전제가 깨졌다는 점을 감안해 기존 표현을 의식적으로 피하거나 이 데이터를 보지 않은 사람에게 맡기는 방안을 검토한다.
- **이번 순서 변경은 1단계에 한정된 일회성 예외다.** 정식 절차(사람 작성 질문 선(先) 봉인, 파일럿과 전체 생성 분리)를 앞으로도 안 지키기로 한 것이 아니라, 1단계가 파이프라인 전체를 처음 구축·검증하는 실험적 단계인 만큼 우선 학습이 실제로 도는지와 대략적인 성능부터 빨리 확인해보고 싶어서 이번 한 번만 이렇게 진행한 것이다. 2단계부터는 3-3 공통 진행 사이클(평가 질문 선(先) 봉인 → 파일럿 → 전체 생성)을 원래대로 따른다.


#### 후속 진행 (2026-09-20)
 - 위 의사결정대로 토크나이저(5번)를 먼저 구현·검증했다 — round-trip 100%(46,090개 문자열, 실패 0), holdout 개체 미등장 풀(고객 60+상품 40=100개) 기준 평균 분할 토큰 수 3.49(임계 4 미만)로 완료 조건 2개를 모두 충족. 이어서 `sql_eval_indist.json`(1,154개 SQL)에도 `question_gen.py` 파이프라인을 `eval_indist1`~`eval_indist6` 6라운드로 돌려 질문 5,770개(1,154×5)를 확보했고, 전 라운드 자동 검증 통과율 100%다 — 123행에서 지적한 "평가용 SQL에는 아직 질문이 없다" 갭이 해소됐다. 남은 보류 항목은 3번(사람 작성 평가 질문 200개)뿐이다.

### 3-4. 학습 시간 추정 근거

**산출 방법**
- 학습 연산량 ≈ 6 × 파라미터 수 × 학습 토큰 수. 여기에 어텐션 연산(최대 컨텍스트 기준 약 3~8%)을 더한다.
- 1단계는 약 4.2e14 FLOPs, 2단계 약 8.3e15, 3단계 약 4.8e16, 4단계 약 2.7e17, 상한 약 1.2e18이다.

**실효 처리량 가정**
- 기준점은 nanoGPT의 shakespeare_char 예제다. 10.65M 파라미터 모델(6층·384차원·컨텍스트 256)을 5,000 iter 학습하는 데 A100 1대로 약 3분(iter당 약 36ms)이 걸린다.
  - 처리 토큰: 5,000 × 배치 64 × 256 = 약 8,200만
  - 연산량: 약 5.5e15 FLOPs
  - 따라서 A100의 실효 처리량은 약 3e13 FLOPs/s다.
- RTX 4070 Super는 A100의 1/2~1/3로 가정해 **1.0e13~1.5e13 FLOPs/s**로 계산했다.

**실측 보정 방법 (1단계 6번 작업에서 수행)**
1. 4070 Super에서 nanoGPT `config/train_shakespeare_char.py`를 설정 변경 없이 실행한다.
2. 로그에서 iter당 시간(초)을 확인한다.
3. 실효 처리량 ≈ **1.1e12 ÷ iter당 초** (이 설정은 iter당 약 1.1e12 FLOPs를 사용한다).
4. 이 값으로 3-2 표의 시간 열을 다시 계산한다.

**해석**
- 1단계 학습이 수 분이면 끝나는 이유는 모델(5M)과 데이터(1,400만 토큰)가 모두 작기 때문이다. nanoGPT의 GPT-2 124M 재현 학습(약 3,000억 토큰)과 비교하면 연산량이 약 50만 분의 1이다. 다만 소형 모델은 GPU 커널 호출 오버헤드 비중이 커서 계산값보다는 느릴 수 있다.
- **학습이 빠르다고 성능이 보장되지는 않는다.** 성능 병목은 GPU 시간이 아니라 데이터 품질과 커버리지다. 짧은 학습 시간은 데이터 수정과 ablation을 여러 번 반복할 수 있다는 장점으로 활용한다.
- **2단계 이후의 병목은 데이터 생성**이다. LLM 호출이 수천~1만 회 이상으로 늘어, 학습보다 생성·검증에 드는 시간과 비용이 더 커진다.

### 3-5. 단계 전환 기준과 예상 성능

**평가 지표**
- 주 지표는 **Exact Match(EM)**: 생성한 SQL이 정답 SQL과 완전히 일치하는 비율이다.
- 보조 지표는 **실행 정확도**: SQLite 실행 결과가 정답과 일치하는 비율이다. 1단계 DB는 행 수가 적어 틀린 SQL도 우연히 같은 결과를 낼 수 있으므로 보조로만 쓴다.
- 모든 지표는 **제약 디코더 적용 전후 두 벌로 측정**한다. 제약 디코더가 DB 값 목록을 참조하면 "미등장 값" 평가를 디코더가 대신 풀어 버리므로, 미적용 수치가 모델의 실제 능력이다. 게이트 판정에는 미적용 수치를 쓴다.
- 200~300문항 규모에서는 EM 70% 지점의 95% 신뢰구간이 ±6%p 안팎이다. 게이트 판정 시 점추정과 함께 신뢰구간을 기록한다.

**1단계 → 2단계 전환 기준**

| 평가 유형 | 내용 | 목표 EM | 예상 EM |
|---|---|---|---|
| 분포 내 | 학습에 없던 SQL, 학습과 같은 프롬프트로 만든 질문 | ≥ 98% | 95% 이상 |
| 미등장 개체 | 학습에 한 번도 나오지 않은 이름·상품명과 그 ID가 들어간 질문 (고객 48명, 상품 24개) | ≥ 90% | 80~95% |
| 미등장 ID | 이름은 학습에 나오지만 ID만 나오지 않은 값이 들어간 질문 (고객 24개, 상품 12개, 주문 45개) | ≥ 90% | 85~95% |
| 새 말투 | 학습과 다른 프롬프트(가능하면 다른 LLM)로 만든 질문 | ≥ 90% | 85~95% |
| 사람 작성 | 사람이 직접 쓴 1단계 범위 내 질문 200개 | ≥ 70%, 규칙 기반 파서 이상 | 60~85% |

- 목표값은 첫 실험 결과를 본 뒤 한 번만 조정할 수 있으며, 조정 사유를 기록한다.
- **예상치의 근거**
  - 분포 내: SQL 구조가 모두 학습에 나오고 값만 바뀌므로 난이도가 낮다.
  - 미등장 개체 / 미등장 ID: 처음 보는 문자열을 여러 토큰 단위로 정확히 복사해야 하므로, 1단계에서 기술적 불확실성이 가장 크다. 이름(문자 subword)과 ID(숫자)는 토큰화 양상이 달라 따로 측정한다.
  - 사람 작성: 학습에 나오지 않은 단어는 모델에게 의미가 없다. 사람이 실제로 쓰는 표현을 LLM 문장이 얼마나 덮는지에 따라 결과가 크게 달라진다.
- **규칙 기반 파서와 비교하는 이유**: 키워드 매칭과 정규식으로 만든 간단한 파서보다 사람 작성 질문에서 나아야 학습 모델을 쓰는 의미가 있다. 1단계 문법은 좁아서 이 베이스라인이 예상보다 강할 수 있다. 베이스라인 개발 시간에 상한을 정하고, 모델 결과를 본 뒤에는 베이스라인을 수정하지 않는다.

**2단계 이후 전환 기준**
- 위 유형에 **"구조 일반화"(학습에서 뺀 SQL 구조 조합)** 평가를 추가한다.
- 목표값은 각 단계 파일럿 결과를 본 뒤 정한다.
- 기존 연구(Finegan-Dollak et al., ACL 2018)에 따르면, 질문 단위로 나눈 평가에서 성능이 좋던 시스템도 SQL 구조가 학습에 없는 평가에서는 크게 고전한다. 따라서 2단계부터는 모델 크기보다 **SQL 구조 조합의 커버리지**가 성능을 결정한다.

### 3-6. 보조 계획

- **Colab 무료 GPU**: 1~2단계 ablation을 병렬로 돌리는 용도로만 쓴다. T4는 bf16을 하드웨어로 지원하지 않으므로 fp16 + GradScaler 경로를 따로 둔다.
- **(선택) 영어 텍스트 사전학습**: 3단계 이후 사람 작성 질문의 정확도가 정체되면, 공개 영어 텍스트로 같은 모델을 무작위 초기화부터 자기지도 사전학습한 뒤 SQL 데이터로 fine-tuning한다. 사전학습 가중치를 가져오지 않으므로 스크래치 원칙에 부합한다.
- **(선택) 한국어 트랙**: 2단계 이후 같은 SQL에 대해 LLM으로 한국어 질문을 생성해 추가한다. BPE 토크나이저는 형태소 분석기 없이 조사가 붙은 표면형을 처리할 수 있다. 리터럴 포함 검사는 조사가 붙은 경우(예: '정경호가')를 허용하도록 한국어용 규칙을 따로 둔다.

## 4. 1단계 범위와 설계 원칙

### 4-1. 스키마 고정
- 3개 테이블(5장)로 스키마를 고정하고, **입력에 스키마 정보를 넣지 않는다**.
  - 컨텍스트 전체를 질문에 쓸 수 있다.
  - 모델은 스키마 이해 없이 "질문 → SQL 변환"만 학습하면 된다.
- 대가: 스키마가 바뀌면 재학습이 필요하다. 이는 specialist 설계에서 감수하는 비용이다.

### 4-2. 언어: 영어
- BPE 토크나이저를 쓰므로 한국어도 형태소 분석기 없이 처리할 수 있다. 그럼에도 1단계를 영어로 하는 이유는 두 가지다.
  1. 조사가 붙지 않아, LLM 문장에 SQL 값이 그대로 들어 있는지 검사하는 규칙이 단순하다.
  2. 사람이 쓰는 평가 질문과 SQL 식별자의 언어가 같아 디버깅이 쉽다.
- 최종 목표가 한국어라면 3-6의 한국어 트랙을 진행한다.

### 4-3. 정규화 규칙
- 질문은 전부 소문자로 변환한다.
- DB의 텍스트 값도 소문자로 저장해, 대소문자 복원 문제를 없앤다.
- SQL 키워드(`SELECT`, `FROM`, `WHERE`)는 대문자로 출력한다.

### 4-4. 1단계 범위에서 제외하는 질문
- JOIN이 필요한 질문 (예: "marilyn이 주문한 상품"은 orders 테이블에 고객 이름이 없으므로 불가)
- 숫자를 영어 단어로 쓴 질문("twenty"), 오타, 값의 동의어·상위어("laptop" → "computer", "sneakers" → "shoes", "sold out" → `stock = 0`)
- 범위 밖 질문에 대한 거절 응답
- 사람 작성 평가에서 이런 질문은 **별도로 집계**하고 정확도 계산에서 제외한다.

## 5. 데이터베이스 스키마

### 5-1. 테이블 구조와 값 도메인

도메인은 **재고 관리(고객-상품-주문)** 다. `orders`를 매개로 `customers`와 `items`가 N:M 관계를 이루며, 이후 JOIN·집계 단계까지 스키마 재설계 없이 확장할 수 있다. 컬럼 수는 4 / 5 / 5개(총 14개)다.

행 수는 원안(80 / 40 / 150)보다 늘렸다. 이유는 5-3에 있다.

**customers (고객, 300행)**

| 컬럼 | 타입 | 값 도메인 |
|---|---|---|
| customer_id | INTEGER PK | 1000~1999 중 무작위 고유값 |
| name | TEXT | **한 단어 이름** (예: marilyn, ashley). 370개 풀에서 중복 없이 추출 |
| city | TEXT | 6종: new york, chicago, houston, seattle, boston, denver. 값마다 최소 38명 |
| membership | TEXT | 4종: bronze, silver, gold, platinum. 값마다 최소 56명 |

**items (상품, 200행)**

| 컬럼 | 타입 | 값 도메인 |
|---|---|---|
| item_id | INTEGER PK | 3000~3999 중 무작위 고유값 |
| item_name | TEXT | **한 단어 상품명** (예: sofa, skateboard). 카테고리별 40개 명사 풀(총 240개)에서 중복 없이 추출 |
| category | TEXT | 6종: electronics, office supplies, kitchen, furniture, clothing, sports. 값마다 최소 25개 |
| price | REAL | 1.00~199.99, 소수점 둘째 자리까지, 저장 시 `round(x, 2)` |
| stock | INTEGER | 0~100, 재고 0(품절)인 상품 최소 13개 |

**orders (주문 내역, 500행)**

| 컬럼 | 타입 | 값 도메인 |
|---|---|---|
| order_id | INTEGER PK | 5000~5999 중 무작위 고유값 |
| customer_id | INTEGER FK → customers | 모든 고객이 최소 1건 (300건) + 무작위 200건 |
| item_id | INTEGER FK → items | 모든 상품이 최소 1건 |
| quantity | INTEGER | 1~10 (10종), 값마다 최소 27건 |
| status | TEXT | 4종: pending, shipped, delivered, cancelled. 값마다 최소 83건 |

상품명 풀은 카테고리별로 분리해 두어, 카테고리와 상품명이 의미상 어긋나지 않는다. 카테고리 배분 시 풀 용량을 상한으로 두어 특정 카테고리가 풀보다 많은 상품을 요구하는 상황을 막는다.

### 5-2. 설계 결정 사항

- **이름을 한 단어로 둔 이유**: 두 단어(`james smith`, `wireless mouse`)보다 토큰 수가 줄어 1단계 학습 부담이 작다. 다만 **복사 문제가 사라지지는 않는다.** vocab 1,024 BPE에서 `marilyn` 같은 이름은 여전히 3~4개 subword로 쪼개지며, 오히려 두 단어보다 분할 경계가 불규칙할 수 있다. 3-3의 5번 작업에서 미등장 이름의 평균 분할 토큰 수를 측정하고, 평균 4토큰을 넘으면 값 풀을 짧은 이름 위주로 재구성하는 것을 검토한다.
- **컬럼명 규칙**: 테이블 간에 이름이 겹치는 컬럼은 FK(customer_id, item_id)뿐이다. 상품명을 `name`이 아닌 `item_name`으로 둔 이유는, 고객의 `name`과 이름이 같으면 SELECT/WHERE 컬럼만으로 테이블을 결정할 수 없는 경우가 생기기 때문이다.
- **ID 대역을 테이블별로 나눈 이유와 부작용**: 실행 결과로 평가할 때 서로 다른 ID 컬럼 사이에서 우연히 결과가 일치하는 경우를 줄이기 위해서다. 그런데 대역이 1000·3000·5000번대로 분리돼 있으면 **첫 자리만 보고 테이블을 맞히는 지름길**이 생긴다. 모델이 질문이 아니라 숫자로 컬럼을 고르게 되므로, SQL 생성기에서 ID 조건 할당량의 일부를 존재하지 않는 ID(결과 0행)로 채워 이 지름길을 깬다. 비율은 5-3에서 정한다.
- **price 등호 비교**: `round(x, 2)`로 저장한 값은 SQL 리터럴 `12.99`와 같은 부동소수점 값이 되므로 `=` 비교가 정확히 동작한다. 상품 200개 전수 단위 테스트로 확인했다. 값 풀이나 행 수를 바꿀 때마다 이 테스트를 다시 돌린다.
- **stock과 quantity의 구분**: 둘 다 "몇 개"를 뜻하는 정수라, "how many … in stock"(재고)과 "how many … ordered"(주문 수량)처럼 주변 단어로 구분해야 한다. 헷갈리기 쉬운 쌍이 스키마에 있다는 것 자체가 유용한 학습 신호가 된다. 평가 시에도 두 컬럼 간 혼동을 따로 집계한다.
- **status를 날짜 대신 쓰는 이유**: 주문일(`order_date`)은 1단계에서 리터럴 형식(`2025-03-14`)과 범위 조건이 필요해 난이도가 높다. 1단계는 범주형 `status`로 두고, 날짜 컬럼은 비교 연산자와 BETWEEN이 들어오는 2단계에서 추가를 검토한다.
- **미등장 값 분리**: 학습 SQL에 절대 나오지 않는 리터럴을 세 층으로 나누어 `holdout.json`에 기록한다. SQL 생성기가 이 파일을 읽어 해당 리터럴을 제외한다.

  | 층 | 대상 | 규모 | 측정 목적 |
  |---|---|---|---|
  | 개체 미등장 | 이름과 ID가 모두 미등장 | 고객 60명(20%), 상품 40개(20%) | 처음 보는 개체 전반 |
  | ID만 미등장 | 이름은 학습에 등장, ID만 미등장 | 고객 30개(10%), 상품 20개(10%) | 숫자 복사 능력만 분리 |
  | 주문 ID 미등장 | order_id | 50개(10%) | 위와 동일 |

  이름(문자 subword)과 ID(숫자)는 토크나이저 입장에서 다른 문제다. 섞어서 측정하면 실패 원인을 가릴 수 없어 분리했다.
- **행 수의 역할**: 원안에서는 "행 수가 1단계 정확도에 거의 영향이 없다"고 보았으나, 행 수가 곧 리터럴 풀이고 리터럴 풀이 곧 SQL 공간이므로 **직접적인 영향이 있다.** 5-3 참조.

### 5-3. SQL 공간과 샘플링 방침

1단계 문법(SELECT 단일 컬럼 또는 `*`, WHERE 단일 등호)으로 만들 수 있는 고유 SQL 수는, WHERE 컬럼별 가용 리터럴 수에 SELECT 선택지 수(컬럼 수 + 1)를 곱해 더한 값이다. 미등장 리터럴을 제외하고 계산하면 다음과 같다.

| 스키마 | 고유 SQL | 그중 ID 조건 | ID 아닌 SQL |
|---|---|---|---|
| 원안 (80 / 40 / 150) | 2,870 | 61% | 약 1,110 |
| 2배 (160 / 80 / 300) | 5,534 | 63% | 약 2,050 |
| 3배, 이름/상품명 풀 원안 유지 (240 / 120 / 450) | 8,126 | 65% | 2,840 |
| **채택 (300 / 200 / 500, 이름 풀 370 / 상품명 풀 240)** | **10,742** | **62%** | **4,052** |

3배 확장(240/120/450) 상태에서 ID 비중 30% 캡을 적용하면 non-ID 풀(2,840개)이 상한이 되어 최대 4,057개(=2,840÷0.7)밖에 못 만들어 학습 4,000 + 평가 1,000 목표를 채우지 못했다. 이름 풀을 300→370개, 카테고리별 상품명 풀을 22→40개(총 240개)로 늘리고 행 수를 300/200/500으로 조정해, ID 비중 30% 캡 안에서 학습 4,609 + 분포 내 평가 1,154 = 5,763개를 실제로 확보했다(`sql_gen.py build --cap-nonid 9999 --cap-id 9999` 기준).

**균등 샘플링을 쓰면 안 된다.** ID 컬럼의 가용 리터럴은 컬럼당 세 자릿수인 반면 city는 6개, membership은 4개, status는 4개다. 균등하게 뽑으면 학습 데이터의 60%대가 "WHERE 무슨_id = 숫자"가 되고, 정작 범주형 조건은 굶는다. 따라서 SQL 생성기는 (테이블 × SELECT 컬럼 × WHERE 컬럼) 조합 단위로 **층화 샘플링**하고 조합별 할당량을 명시한다. ID 조건 총량은 전체의 30% 이하로 제한한다.

미결 사항은 두 가지이며, SQL 생성기 구현 시 확정한다.

1. ID 조건 중 존재하지 않는 ID(결과 0행)의 비율. 5-2의 지름길 문제를 깨는 대신 실행 정확도 지표의 해상도를 떨어뜨리는 맞교환이다. 현재 안은 20%다.
2. SELECT `*` 를 1단계에 포함할지 여부. `*` 와 특정 컬럼을 자연어 질문만으로 구분하기 어려워 라벨 노이즈원이 된다. 파일럿에서 `*` 질문의 검증 통과율을 따로 집계해 판단한다.

### 5-4. 재현

DB는 `db_gen.py` 로 생성하며 시드를 고정하면 항상 동일한 결과가 나온다.

```
python db_gen.py test       # 분포 조건 / 결정성 / price 등호 / 미등장 값 4종
python db_gen.py build      # data/shop.db, data/holdout.json
python db_gen.py space      # SQL 공간과 ID 조건 비중
```

`--preset small` 로 원안 스키마를, `--name-style two_word` 로 두 단어 이름을 다시 만들 수 있다. 결정성 판정은 SQLite 파일 바이트가 아니라 행 내용 기준 해시로 한다.

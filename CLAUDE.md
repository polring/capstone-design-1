## Scratch-build constraint (critical)

Model, tokenizer, training loop, and inference are implemented from scratch — that is the point of the
project.

| | Allowed | Forbidden |
|---|---|---|
| Libraries | Python stdlib, PyTorch (tensor ops/autograd/optimizer only), SQLite, NumPy, TensorBoard | HuggingFace `tokenizers`/`transformers`, SentencePiece, tiktoken, any off-the-shelf model/tokenizer |
| Weights | Random init only | Pretrained checkpoints |
| Data | DB/SQL generated by code; questions by an external LLM; some eval questions hand-written | An LLM generating or modifying ground-truth SQL |
| Reference | nanoGPT may be read and rewritten | — |

## Data layout and paths

All paths live in `src/config.py` and follow `STAGE` (`config.stage_paths(N)` for another stage). Every command
takes its input files and output location as arguments and falls back to these defaults — don't hardcode paths.
Roles come from **folder position**, not names:

- `data/stage<N>/train/*.json` — **every** JSON here is training data and BPE corpus. Never put eval pairs here.
- `data/stage<N>/eval/<name>/` — one eval set per folder: `pairs.json` + `sql.json` (metadata of the SQL used,
  incl. `holdout_tier`). Build `sql.json` with `python -m src.run --build-sql <name> --sql <sql file>`, never by hand;
  loading fails if a pair's SQL is missing from it. `holdout_qwen` is the old Qwen-written set, kept for comparison only.
- `data/stage<N>/tokenizer/seed_tokens.json` — seed IDs are `260 + list order`: reordering or inserting changes
  every token ID, so retrain BPE and the model after editing. `tokenizer.json` is the trained result (seeds + merges).
- `models/stage<N>/` — the one committed release (`model.pt` + the `tokenizer.json` it was trained with +
  `model_info.json`), made by `python -m src.release`. Never write eval/prediction outputs here; they go to `runs/`.
- `data_raw/`, `runs/` — uncommitted. Question-generation rounds are validated in `data_raw/` and moved by hand.
- Stage-specific code lives in `src/data/stage<N>/` (SQL/question generation, label cleaning, name swap,
  scoring rules `sql_rules.py`); `src/evaluation/scoring.py` keeps only stage-independent scoring.

## Design decisions that are easy to undo by accident

- **Loss on SQL tokens only** (`loss_mask`); the question is given at inference.
- **Right padding without an attention mask is correct** for this causal decoder. Batched generation must
  group prompts of equal length (`generate_batch` in `src/inference/generate.py`).
- **`FFN_DIM = round(8d/3)`**: SwiGLU has 3 matrices, so this matches the plan's parameter budget
  (GELU 4d, 2 matrices). Don't revert to `3d`/`4d`.
- **Validation split is by SQL, not by pair**, and `eval_indist` is never used for checkpoint selection —
  otherwise scores measure memorization.
- **Holdout literals** (`data/stage<N>/db/holdout.json`) must never appear in training SQL (`db_gen.load_bans()`).
- BPE seed tokens (SQL keywords, columns, categorical values) stay single tokens; merge ties break
  deterministically.
- Text values lowercase, SQL keywords uppercase.
- **One question, one SQL**: labels follow the plan's 4-5 label rules (L1–L5). Training data is cleaned with
  `python -m src.data.stage1.clean_ambiguous --apply` (re-run after adding pairs; rebuild BPE after). Eval sets are
  left as-is for comparability. `sql_rules.select_ambiguous` is a frozen metric rule — don't edit it to match
  the label rules.
- **Rule-consistent EM** (`rule_consistent` in eval results) drops eval items whose gold label violates the label
  rules, using the same `clean_ambiguous.drop_reason` (via `sql_rules.label_mismatch`). Stage-1 in-dist is gated on
  it. Never tune those rules by looking at eval failures — change them only from training data, then re-clean.

## LLM question generation rules

- One independent LLM session per batch — a session handling a whole round converges on stock phrasings.
- Don't let the generating session write a generator script; read real sentences, since `validate()` and
  `template_check()` can be gamed (a 0% repeat ratio is a reason to inspect, not a pass).
- Keep the checker's internals out of the generating session's context.
- Local models (Qwen3-14B) ignore rule 10 (existence-check framing when `select == where_col`); filter
  with `soft_flags()`.
- After merging new pairs, run `python -m src.data.stage1.question_gen corpus-check` and remove both sides of
  any label conflict.

## Commands

Run from the repo root with `.venv\Scripts\python` (paths are cwd-relative). Full list: SETUP.md.

```
python -m pytest tests/ -v          # unit tests
python -m src.train --overfit 100   # pipeline sanity check: must reach EM 100%
python -m src.train                 # full training (name swap 40% per epoch) + final eval -> runs/stage<N>/ffn<D>_swap40/
python -m src.release --ckpt runs/stage<N>/<run>/best.pt   # -> models/stage<N>/ (the committed release)
python -m src.run --evaluation      # score the release on every eval set (--model / --eval-sets to change)
python -m src.run --input "..."     # question -> SQL -> shop.db result (no --input: interactive)
python -m src.demo all              # follow one example through every stage, input -> output
```

`src/` root holds only `config.py` and the commands above (`python -m src.<name>`); libraries live in subpackages —
`src/inference/` (loading, generate) and `src/evaluation/` (scoring, eval_sets) have no command line.

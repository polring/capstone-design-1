# 🤝 캡스톤 프로젝트 팀 협업 규칙 (Convention)

본 문서는 프로젝트 진행 중 팀원 간의 원활한 소통과 코드 품질 및 Git 관리를 위해 작성된 규칙입니다.

---

## 🌿 1. 브랜치 전략 (Branch Strategy)

- **구조**: 2단계 단일 브랜치 중심 (GitHub Flow 변형)
- **`main`**: 항상 실행 및 빌드가 가능한 최신 브랜치 (직접 Push 금지, PR 필수)
- **작업 브랜치**: 이슈 단위로 `main`에서 생성 후 머지 완료 시 삭제

### 브랜치 명명 규칙
- **신규 기능**: `feat/#이슈번호-간단한설명` (예: `feat/#2-tokenizer`)
- **버그 수정**: `fix/#이슈번호-간단한설명` (예: `fix/#4-rope-bug`)
- **문서 및 규칙**: `docs/#이슈번호-간단한설명` (예: `docs/#1-convention`)

---

## 📝 2. 커밋 메시지 규칙 (Commit Convention)

커밋 메시지는 `[Prefix]: [작업 내용]` 형태로 작성합니다.

- `feat:` 새로운 기능 구현
- `fix:` 버그 수정
- `docs:` README, 협업 규칙, 주석 등 문서 수정
- `refactor:` 코드 구조 및 가독성 개선 (기능 변경 없음)
- `style:` 코드 포맷팅, 세미콜론 누락 등 (로직 변경 없음)

> **예시**: `docs: add PR template and convention guide`

---

## 🔄 3. PR 및 리뷰 수칙 (PR & Code Review)

1. **PR 올리기 전**: 로컬 환경에서 코드 실행 및 입력/출력 텐서 Shape 정상 동작 여부를 직접 확인합니다.
2. **리뷰어 지정**: PR 올린 후 팀원 중 1명 이상에게 코드 리뷰 요청 (카톡/슬랙 알림).
3. **승인 및 머지**: 최소 **1명의 승인(Approve)**을 받은 후 **`Squash and merge`**로 `main`에 합칩니다.
4. **브랜치 삭제**: 머지 직후 사용했던 작업 브랜치는 삭제합니다.

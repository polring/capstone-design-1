# Text-to-SQL 1단계 진행 보고서

최종 갱신: 2026-10-04

1단계(단일 테이블, `SELECT` 단일 컬럼 또는 `*`, `WHERE` 단일 등호) 진행 상황을 정리한다. 앞부분은 현재
상태와 구성, 뒷부분 "활동 기록"은 날짜별로 무엇을 했고 왜 그렇게 결정했는지를 남긴다. 단계 계획과 작업별
완료 조건은 [계획서](text-to-sql-llm-project-plan.md) 3-3절에 있다.

## 현재 상태

| 순서 | 작업 | 상태 |
| --- | --- | --- |
| 1 | DB 생성기 구현 | 완료 |
| 2 | SQL 생성기 구현 | 완료 |
| 3 | 사람 작성 평가 질문 200개 작성·봉인 | 보류 (2026-09-19 결정) |
| 4 | LLM 질문 생성 파일럿 | 완료 (2026-09-19) |
| 5 | BPE 토크나이저 구현 | 완료 (2026-09-20) |
| 6 | 모델·학습 루프 구현 | 완료 (2026-10-01) |
| 7 | 전체 데이터 생성 (분포 내 평가 질문 포함) | 완료 (자동 검증 기준, 수동 감사 미실시) |
| 8 | 학습·평가·ablation | 진행 중 — 이름 교체 40%(epoch마다) + 라벨 정제 데이터로 학습. seed 3개 기준 분포 내 EM 96.3~96.7%(목표 98% 미달), 미등장 개체 88.6~90.2%(목표 90% 경계), 미등장 ID 88.9~89.7%(미달), 미등장 주문 ID 94.4~96.0%(통과). 새 말투·사람 작성 평가, 제약 디코더, ablation은 2단계로 미룸 |

### 코드

| 파일 | 역할 |

| `src/models/transformer.py` | RMSNorm, causal self-attention, SwiGLU FFN, 디코더 블록 |
| `src/models/model.py` | 전체 decoder-only 모델 조립, greedy `generate` |
| `src/train.py` | 학습 루프(기본: epoch마다 이름 교체 40%), 과적합 테스트, 학습 후 평가셋 측정 |
| `src/data/clean_ambiguous.py` | 라벨 규칙(계획서 4-5 L2~L4)과 어긋나는 학습 쌍 제거 |

| `src/config.py` | `STAGE` 값으로 단계별 모델 구조 선택 |

### 모델·학습 설정

| 항목 | 값 |
| --- | --- |
| 구조 | 6층 · 256차원 · 4헤드, RoPE, RMSNorm(Pre-LN), SwiGLU FFN 683, 임베딩-출력층 가중치 공유 |
| 파라미터 | 4,985,600개 (계획서 5.02M) |
| 학습 | AdamW(β 0.9/0.95, weight decay 0.1), lr 1e-3, warmup 200 step → cosine, grad clip 1.0, bf16, 배치 32 |
| 이름 교체 | 매 epoch 시작 때 학습 분할의 이름 조건 쌍(7,989개)의 40%를 질문·SQL 양쪽에서 새 가짜 이름으로 교체 (`--name-swap-ratio`, 0이면 끔). 검증셋은 교체하지 않은 원본 |
| 검증 | 학습 쌍에서 SQL 단위로 5% 분리 (학습 21,404 / 검증 1,080쌍) |
| 종료 | 최대 25 epoch, 검증 EM이 10 epoch 연속 개선되지 않으면 조기 종료, 검증 EM 최고 시점 체크포인트 저장 |

**결과** — 기본 모델 `stage1_ffn683_swap40`(이름 교체 40%, seed 0, 같은 설정의 seed 1·2는 `_s1`·`_s2`)과
이름 교체 없는 기준 실행 `stage1_ffn683`(seed 0). 모두 라벨 정제 후 학습 데이터로 학습했다.

| 항목 | 기본 모델 | 기준 실행 |
| --- | --- | --- |
| 과적합 테스트 (예시 100개) | 1,200 step에서 EM 100% | 같음 |
| 검증 EM (최고) | 99.0% (24 epoch) | 97.7% (24 epoch) |
| 학습 시간 (25 epoch) | 527초 (이름 교체·재토큰화 포함) | 292초 |
| 실효 처리량 | — | 약 9.1만 토큰/s, 2.7e12 FLOPs/s (계획서 가정 1.0~1.5e13의 약 1/4) |

**평가 결과** (`src/evaluation.py`, 제약 디코더 미적용)

| 평가 유형 | 쌍 수 | 기본 모델 EM [95% CI] | 실행 정확도 | seed 0 / 1 / 2 | 기준 실행 EM | 계획서 목표 | 판정 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 분포 내 | 5,202 | **96.7%** [96.2, 97.1] | 96.9% | 96.7 / 96.3 / 96.4 | 95.5% | ≥ 98% | 미달 |
| 미등장 개체 | 1,480 | **90.2%** [88.6, 91.6] | 90.4% | 90.2 / 90.2 / 88.6 | 60.9% | ≥ 90% | 경계 |
| 미등장 ID | 497 | **89.7%** [86.8, 92.1] | 89.9% | 89.7 / 88.9 / 89.7 | 90.1% | ≥ 90% | 미달 |
| 미등장 주문 ID | 249 | **96.0%** [92.8, 97.8] | 96.0% | 96.0 / 94.4 / 95.2 | 94.8% | ≥ 90% | 통과 |

- 미등장 개체는 seed 2개가 90.2%, 1개가 88.6%(평균 89.7%)이고 신뢰구간 하한도 90% 아래라 통과로 보지 않는다.
- 다중 정답 EM(SELECT 모호 문항에서 `*` ↔ 식별 컬럼 교체 인정)은 기본 모델 분포 내 97.3%, 미등장 값 90.7%다.
- 처음 보는 이름 정답률(WHERE 컬럼별 EM)은 기본 모델 고객 88.1%(294쌍)·상품 88.5%(200쌍), 기준 실행 0.3%·0.0%다.
  남은 오답은 대부분 SELECT 선택 오류다(분포 내 173개 중 112개, 미등장 값 206개 중 171개).
- 세 seed 모두 최고 검증 EM이 21~24 epoch에서 나와, 상한(25 epoch)을 늘리면 더 오를 여지가 있다.

**학습 시간: 계획 추정과 실측**

계획서 3-2의 학습 시간은 연산량(6 × 파라미터 수 × 학습 토큰 수)을 실효 처리량으로 나눠 추정했다. 처리량은
nanoGPT shakespeare_char 예제(10.65M 모델, A100에서 iter당 약 36ms → 약 3e13 FLOPs/s)를 기준으로,
4070 Super를 A100의 1/2~1/3인 1.0~1.5e13 FLOPs/s로 가정했다. 원래는 같은 예제를 4070 Super에서 돌려
보정할 계획이었으나, `src/train.py`로 실제 학습을 돌려 직접 측정했다.

- 1단계는 추정("수 분")과 실측(기준 실행 25 epoch 292초)이 맞는다.
- 처리량은 가정의 약 1/4이다. 이 값을 그대로 쓰면 2단계(약 8.3e15 FLOPs)는 9~14분이 아니라 약 50분이
  된다. 다만 1단계 처리량은 작은 모델의 커널 호출 오버헤드에 묶인 값이라, 큰 모델에서는 처리량이 올라갈
  가능성이 높다. 2단계 시작 시 다시 측정해 보정한다.
- 학습 시간보다 데이터 품질·커버리지가 성능을 좌우하고, 2단계 이후의 병목은 LLM 호출 수(수천~1만 회)가
  늘어나는 데이터 생성이다.

### 2026-09-19 — 학습 질문 생성 완료, 진행 순서 변경 결정

- DB 생성기(1번)와 SQL 생성기(2번)가 완료 조건을 통과한 상태에서, LLM 질문 생성(4번)을 13라운드 누적해
  학습 쌍 23,045개(SQL 4,609 × 5)를 확보했다. 전 라운드 자동 검증 통과율 100%.
- 표현 다양성: 한 LLM 세션이 라운드 전체를 처리하면 같은 `(SELECT, WHERE)` 조합이 10여 번 넘게 나오는
  순간 문장이 소수 틀로 수렴했다(반복 골격 비율 32~77%). 배치(SQL 25개)마다 독립된 세션을 쓰는 방식으로
  바꾼 pilot6 이후 15~20%대로 안정됐다. pilot13(55쌍)만 반복 비율 0%였는데, 전량 읽어 보니 실제로 다른
  단어를 쓴 정상적인 다양성이었다. 다만 SQL마다 격식체 → 캐주얼체 → 키워드체 순의 같은 "말투 로테이션"을
  반복하는 패턴은 있었다.
- 계획과 달라진 점:
  - 계획의 공통 사이클(3-3)은 "사람 작성 평가 질문 봉인 → 파일럿 → 전체 생성" 순서인데, 실제로는 3번을
    건너뛰고 파일럿 절차를 13번 반복해 전체 생성까지 끝냈다. 파일럿과 전체 생성이 사실상 하나의 과정이
    됐지만, `question_gen.py`의 라운드 누적·`--exclude-dir` 구조가 이 방식에 맞아 문제는 없었다.
  - 질문 생성 입력이 전부 `sql_train.json`이라 분포 내 평가 SQL(1,154개)에는 아직 질문이 없었다
    (2026-09-20에 해소).
- 결정: 사람 작성 평가 질문(3번)과 분포 내 평가 질문 생성을 보류하고 토크나이저(5번)를 먼저 진행. 이미
  LLM 문장을 본 뒤라 "봉인 후 작성" 전제가 깨졌으므로, 나중에 작성할 때는 기존 표현을 의식적으로 피하거나
  데이터를 보지 않은 사람에게 맡긴다. 이 순서 변경은 파이프라인을 처음 구축하는 1단계에서 학습이 실제로
  도는지부터 빨리 확인하려는 일회성 예외이며, 2단계부터는 계획의 공통 사이클을 원래대로 따른다.

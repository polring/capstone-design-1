# Text-to-SQL 1단계 진행 보고서

최종 갱신: 2026-10-05

1단계 범위는 단일 테이블, `SELECT` 컬럼 하나 또는 `*`, `WHERE` 등호 조건 하나다. 이 문서는 지금 어디까지
왔는지(1~2절), 계획과 무엇이 달라졌는지(3절), 언제 무엇을 했는지(4절), 무엇이 남았고(5절) 무엇을 하지 않기로 했는지(6절)를 정리한다.
작업별 완료 조건은 [계획서](text-to-sql-llm-project-plan.md) 3-3절, 실행 방법은 [SETUP](SETUP.md)에 있다.

## 1. 현재 상태

데이터 생성 → 토크나이저 → 모델 → 학습 → 평가 → 추론까지 파이프라인 전체가 동작한다. 처음 보는 이름을 거의
복사하지 못하던 문제는 크게 개선했지만(0~3% → 약 88%), 1단계 → 2단계 전환 기준은 아직 넘지 못했다(2절).

| 순서 | 작업 | 상태 |
| --- | --- | --- |
| 1 | DB 생성기 구현 | 완료 |
| 2 | SQL 생성기 구현 | 완료 |
| 3 | 사람 작성 평가 질문 200개 작성·봉인 | 보류 (3절) |
| 4 | LLM 질문 생성 파일럿 | 완료 |
| 5 | BPE 토크나이저 구현 | 완료 |
| 6 | 모델·학습 루프 구현 | 완료 |
| 7 | 전체 데이터 생성 | 완료 (자동 검증 기준, 수동 감사 미실시) |
| 8 | 학습·평가·ablation | 진행 중 — 학습·평가 완료, 전환 기준 미달. 새 말투·사람 작성 평가, 제약 디코더, ablation은 남음 |

## 2. 결과

### 전환 기준 판정

기본 모델(`runs/stage1_ffn683_swap40`, 이름 교체 40% + 라벨 정제 데이터)을 seed 3개로 학습한 결과다.
제약 디코더는 적용하지 않았다.

| 평가 | 쌍 수 | 목표 | EM (seed 0 / 1 / 2) | 판정 |
| --- | --- | --- | --- | --- |
| 분포 내 (학습에 없던 SQL) | 5,202 | ≥ 98% | 96.7 / 96.3 / 96.4% | 미달 |
| 미등장 개체 (처음 보는 이름·ID) | 1,480 | ≥ 90% | 90.2 / 90.2 / 88.6% | 경계 |
| 미등장 ID (이름은 학습에 있고 ID만 처음) | 497 | ≥ 90% | 89.7 / 88.9 / 89.7% | 미달 |
| 미등장 주문 ID | 249 | ≥ 90% | 96.0 / 94.4 / 95.2% | 통과 |
| 새 말투 · 사람 작성 | — | ≥ 90% · ≥ 70% | 미측정 | 2단계로 미룸 |

- **미등장 개체는 통과로 보지 않는다.** seed 0의 95% 신뢰구간이 [88.6, 91.6]으로 90%에 걸쳐 있고 seed 하나는 88.6%다.
- **이름 복사는 크게 개선됐다.** 처음 보는 이름 정답률이 이름 교체 없이 학습하면 고객 0.3% · 상품 0.0%, 이름 교체로 학습하면 88.1% · 88.5%다.
- **남은 오답은 대부분 SELECT 컬럼 선택이다.** 분포 내 오답 173개 중 112개, 미등장 값 206개 중 171개. 존재 확인
  질문("do we carry a bench")에 `SELECT *`로 답하는 경우처럼 의미상 맞지만 라벨 관례와 다른 답이 상당수다(5절).
- 다중 정답 EM(`*`와 이름 컬럼 중 무엇을 원하는지 질문에 단서가 없는 문항은 둘 다 정답 인정)은 분포 내 97.3%, 미등장 값 90.7%다.

### 알려진 한계

- 평가셋은 라벨 규칙(계획서 4-5)으로 정제하지 않았다. 규칙과 라벨이 다른 문항(분포 내 60, 미등장 값 58)에서는 정답을 내도 오답 처리될 수 있다.
- 미등장 값 오답이 소수 SQL에 몰려 있어, 쌍 단위로 낸 신뢰구간은 실제보다 좁다.
- 평가셋에 없는 유형: 숫자가 둘 이상인 질문, 긴 숫자, 따옴표로 감싼 값. `predict.py`로 시험해 보면 이런 질문에 약하다.

## 3. 계획과 달라진 점

| 항목 | 계획 | 실제 | 이유 |
| --- | --- | --- | --- |
| DB 행 수 | 80 / 40 / 150행 | 300 / 200 / 500행, 이름 풀 370 · 상품명 풀 240 | 원안은 고유 SQL 2,870개(ID 아닌 SQL 약 1,110개)로, ID 조건 30% 이하에서 학습 4,000 + 평가 1,000을 못 채움. 3배(240 / 120 / 450)도 최대 약 4,057개라 이름·상품명 풀까지 늘림 |
| 진행 순서 | 사람 작성 평가 질문을 먼저 봉인한 뒤 데이터 생성 | 사람 작성 평가(3번)를 보류하고 학습부터 진행 | 파이프라인이 실제로 도는지 먼저 확인하려는 1단계 한정 예외. 2단계부터 원래 순서 |
| 질문 생성 방식 | — | 배치(SQL 25개)마다 독립된 LLM 세션 | 한 세션이 라운드 전체를 맡으면 문장 틀이 소수로 수렴(반복 비율 32~77% → 15~20%) |
| 학습 데이터 출처 | 외부 LLM | 강한 LLM + 로컬 Qwen3-14B 일부 | Qwen3는 규칙 일부를 무시해 걸러서 보조로만 사용 |
| FFN 크기 | GELU 4d 기준 예산 | SwiGLU `round(8d/3)` = 683 | SwiGLU는 행렬이 3개라 같은 파라미터 예산이 되는 크기로 맞춤 |
| 조기 종료 | — | 10 epoch 개선 없으면 종료 | 검증 EM이 epoch마다 ±2%p 흔들려 5 epoch 기준은 너무 일찍 끊김 |
| 이름 교체 학습 | 없음 | 기본 학습 방식으로 채택 | 첫 학습에서 처음 보는 이름 정답률 0~3%. 모델이 질문에서 복사하지 않고 학습한 이름 목록을 외웠음 |
| 라벨 규칙 | 없음 | 계획서 4-5 L1~L5 신설, 학습 데이터 378쌍 제거 | 같은 표현에 다른 정답이 붙어 있었음(예: "which item ~" → 이름 197개 / `*` 24개) |
| 미등장 값 평가셋 | — | Qwen3 생성본을 강한 LLM으로 재생성 | Qwen3 평가셋은 문형이 좁아 점수가 높게 나왔음(미등장 개체 약 94% → 재생성 후 약 88%) |
| 평가 지표 | EM, 실행 정확도 | 다중 정답 EM 추가 | `*`와 이름 컬럼 중 무엇을 원하는지 질문만으로 알 수 없는 문항이 분포 내 6% |
| 학습 처리량 | 1.0~1.5e13 FLOPs/s 가정 | 2.7e12 (약 1/4) | 작은 모델이라 커널 호출 오버헤드 비중이 큼. 1단계 학습 시간에는 영향 없고, 2단계 시작 때 다시 측정 |

## 5. 남은 작업

우선순위는 전환 기준 판정에 미치는 영향과 드는 비용(재학습 필요 여부, 사람 작업량)으로 정했다.

| 순위 | 작업 | 내용 | 기대 효과 |
| --- | --- | --- | --- |
| 1 | 존재 확인 질문 채점 방식 | "do we carry a bench" → `SELECT *`처럼 의미상 맞지만 라벨 관례(L1)와 다른 답을 어떻게 채점할지 정함 | 미등장 값 EM이 실제 능력보다 낮게 나오는 가장 큰 원인 해소 (정제 전 분석에서 미등장 값 오답의 42%). 재학습 불필요 |
| 2 | 평가 보조 지표 | 라벨 규칙과 다른 평가 문항을 뺀 EM, L5 문항 EM, SQL 단위 신뢰구간 | 라벨 불일치 문항(분포 내 60, 미등장 값 58) 때문에 깎인 점수를 걷어 내고, 신뢰구간을 실제 크기로 봄. 평가 코드만 수정 |
| 3 | ablation | 모델 축소(4층·192차원), FFN 크기 비교 | 계획서 2장의 "데이터 대비 모델이 커서 암기한다"는 우려 확인. 작은 모델이 미등장 값에서 같거나 나으면 2단계 설계에 반영. 1회 약 10분 × seed 3개 |
| 4 | 제약 디코더 | DB 값·문법에 맞는 토큰만 생성, 적용 전후 두 벌 측정 | 형식이 깨진 SQL과 없는 컬럼·값 출력을 차단해 실사용 정확도 상승. 게이트 판정은 미적용 수치로 하므로 판정 결과는 바뀌지 않음 |
| 5 | 새 말투 · 사람 작성 평가 | 다른 프롬프트(가능하면 다른 LLM)로 만든 질문, 사람이 쓴 질문 200개(3번 작업) | 전환 기준의 남은 두 항목을 채우고, LLM 문장 밖의 실제 표현에서 얼마나 되는지 확인. 사람 작업량이 커서 2단계로 미뤄 둠 |

## 6. 하지 않기로 한 작업

검토했지만 들이는 비용에 비해 얻는 것이 작다고 판단했다. 상황이 바뀌면(괄호 안 조건) 다시 본다.

| 작업 | 내용 | 하지 않는 근거 |
| --- | --- | --- |
| epoch 상한 조정 | 최고 검증 EM이 21~24 epoch에서 나와 25 epoch 상한을 늘려 보는 것 | 세 seed 모두 마지막 5~6 epoch의 검증 EM 변동이 ±0.5%p(검증 1,080쌍 중 대여섯 문항) 안으로 이미 평평하다. 끝 무렵이 최고인 것은 cosine 학습률이 25 epoch에 맞춰 최솟값으로 내려가기 때문이라 학습이 덜 됐다는 근거가 아니다. 남은 오답 대부분은 SELECT 선택(라벨·표현 문제)이라 학습을 더 해서 줄어들 성격이 아니다. (모델 크기나 데이터 양이 바뀌면 다시 확인) |
| `soft_flags()`에 라벨 규칙 반영 | 질문 생성 직후 검증(`validate`)에서 L2~L4 위반을 경고 | 성능에 영향이 없다. 병합 후 `clean_ambiguous --apply`가 같은 규칙으로 위반 쌍을 지우는 절차가 이미 있어, 얻는 것은 "더 일찍 발견"뿐이다. `clean_ambiguous`는 torch를 거쳐 import되므로 표준 라이브러리만 쓰는 질문 생성 스크립트에 넣으려면 규칙 판정부를 따로 분리해야 한다. (2단계에서 라벨 규칙이 늘어나 위반이 많아지면 다시 검토) |

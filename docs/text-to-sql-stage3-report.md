# Text-to-SQL 3단계 진행 보고서

최종 갱신: 2026-10-19

3단계에서는 날짜 조건, 합계·평균 등의 집계, GROUP BY·HAVING, 서브쿼리를 추가했다.
예를 들어 “고객별 주문 수량 합계”나 “평균보다 재고가 많은 상품”을 SQL로 바꾸는 단계다.

## 요약

같은 데이터로 5.8M과 15.7M 모델을 학습하고, 질문을 익숙한 표현으로 바꾸는 전처리기를 비교했다.
**15.7M은 새로운 SQL 구조 조합에 강했고, 전처리기는 낯선 표현을 처리하는 데 효과가 컸다.**

15.7M의 고급 구조 정확도는 97.10%, 전처리를 포함한 고급 표현 정확도는 76.08%다.
이를 바탕으로 4단계 JOIN 파일럿을 다음 작업으로 제안했다. 남은 주요 약점은 서브쿼리의 조건 범위와 자연스러운 사용자 표현이다.

## 1. 평가 결과

두 모델은 같은 학습 데이터·토크나이저로 비교했다. **원문**은 모델에 질문을 그대로 넣은 결과,
**전처리**는 도메인 단어·집계 표현·약어·기호를 바꾼 뒤 넣은 결과다. 수치는 모두 정답 SQL과 일치한 비율인 EM(%)다.

기본 평가는 학습하지 않은 SQL, 미등장 값 평가는 처음 보는 이름·ID·날짜를 사용한다.
표현 변형은 같은 뜻의 다른 말투, 구조 변형은 학습에서 제외한 SQL 조합을 평가한다.

| 평가 | 문항 | 5.8M 원문 | 5.8M 전처리 | 15.7M 원문 | 15.7M 전처리 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 일반 기본 | 2,000 | 98.75 | 98.75 | 98.80 | 98.80 |
| 일반 미등장 값 | 7,161 | 99.72 | 99.72 | 99.83 | 99.83 |
| 일반 표현 변형 | 2,000 | 83.75 | 83.75 | 83.85 | 83.95 |
| 일반 구조 변형 | 1,978 | 85.19 | 85.19 | 86.30 | 86.35 |
| 고급 기본 | 1,000 | 97.50 | 97.50 | 97.80 | 97.80 |
| 고급 미등장 값 | 1,546 | 99.81 | 99.81 | 99.87 | 99.87 |
| **고급 표현 변형** | **991** | **52.77** | **78.10** | **52.07** | **76.08** |
| **고급 구조 변형** | **1,000** | **86.90** | **87.00** | **97.10** | **97.10** |
| 사람 말투 반영 LLM | 1,000 | 69.00 | 73.30 | 69.90 | 73.50 |

고급 표현 정답은 전처리로 5.8M에서 **251개**, 15.7M에서 **238개** 늘었다.

### 사람 말투를 반영한 평가

2단계의 사람 작성 말투를 참고해 LLM이 만든 1,000문항이다. 실제 사람이 작성한 3단계 평가셋은 아니다.
같은 SQL 200개를 다섯 가지 말투로 물었으며, 유형별 결과는 다음과 같다.

| SQL 유형 | 문항 | 5.8M 원문 → 전처리 | 15.7M 원문 → 전처리 |
| --- | ---: | ---: | ---: |
| 일반 조회 | 250 | 70.80 → 72.40 | 75.20 → 76.40 |
| 단일 집계 | 200 | 74.00 → 75.00 | 73.50 → 74.00 |
| GROUP BY | 200 | 82.50 → 92.50 | 83.00 → 93.50 |
| HAVING | 175 | 54.86 → 60.00 | 71.43 → 76.57 |
| 스칼라 서브쿼리 | 175 | 59.43 → 64.00 | 41.71 → 42.86 |

기호·약어 질문은 5.8M에서 33.50→53.00%, 15.7M에서 33.00→50.50%로 올랐다.
다만 전체 점수가 비슷해도 유형별 차이는 크다. 15.7M은 HAVING에 강하지만, 이 평가의 서브쿼리는 5.8M보다 낮다.

## 2. 남은 오답의 원인

| 문제 | 확인된 모습 |
| --- | --- |
| 질문에 없는 조건 추가 | 요청하지 않은 상품 범주나 주문 상태를 WHERE에 붙임 |
| 조건의 적용 범위 혼동 | 평균을 구할 집단의 조건과 최종 조회 대상의 조건을 바꿈 |
| 집계값과 행 조회 혼동 | 최댓값을 묻는데 해당 값을 가진 상품을 조회하거나 GROUP BY·정렬을 추가함 |
| 낯선 말투·문자열 복사 | 기호·어색한 영어에서 조건을 빠뜨리거나 LIKE 검색 조각을 다르게 출력함 |

전처리 후에도 사람 말투 평가의 서브쿼리 정확도는 15.7M에서 42.86%다.
단어를 익숙하게 바꾸는 것만으로 조건의 역할과 적용 범위까지 해결되지는 않았다.

## 3. 실험에서 얻은 결론

**모델 크기는 구조 조합에 도움이 됐다.** 15.7M은 고급 구조 평가에서 5.8M보다 약 10%p 높았다.
하지만 원문 고급 표현 점수는 두 모델 모두 52%대여서, 크기 확대만으로 표현 문제를 해결하지 못했다.

**전처리는 학습 표현과 사용자 표현의 차이를 줄였다.** `articles`를 `items`로, `avg qty`를 `average quantity`로
바꾸는 방식이다. WordNet의 의미 관계와 사람이 정한 도메인·구문 규칙을 사용하며, 모델 재학습은 필요하지 않았다.

**보강은 양과 비율을 함께 봐야 했다.** 숫자 보강 등의 설정을 바꾼 뒤 5.8M의 HAVING+LIMIT 정답은
334문항 중 44→244개로 회복했다. 다만 분할·LIKE 방식·학습량도 함께 바뀌어 숫자 보강 하나의 효과로 단정할 수 없다.

## 6. SQL 생성과 라벨 정책

| 영역 | 지원 범위 |
| --- | --- |
| 일반 조회 | 단일 테이블, 출력 컬럼 하나 또는 전체, 조건 최대 3개, IN·LIKE·정렬·LIMIT |
| 집계·그룹 | COUNT/AVG/SUM/MIN/MAX, 집계식·그룹 키·HAVING 조건 각각 하나 |
| 고급 조건 | AND 연결, 서브쿼리 바깥과 안쪽에 각각 최대 2조건 |
| 스칼라 서브쿼리 | 같은 테이블의 숫자 컬럼, 깊이 1, 비상관 서브쿼리 |

빈 결과·COUNT=0·NULL도 유효한 결과로 취급한다. 기본 동점 정렬은 자기 기본키 ASC이며 명시적 요청이 우선한다.
JOIN, 여러 집계식·그룹 키, AND/OR 혼합, 상관·중첩 서브쿼리는 현재 구현 범위 밖이다.
세부 의미 규칙은 [라벨 규칙 문서](text-to-sql-label-rules.md)를 따른다.

## 7. 학습 데이터와 전처리

최신 비교는 **학습 321,041쌍·검증 16,216쌍**을 고정했다. 같은 검증 SQL을 쓰는 보강 115쌍과,
이들과 함께 비교하도록 만든 문항 90쌍을 제외했다. HAVING+LIMIT 조합은 학습에 넣지 않고 구조 평가로 남겼다.

numbers r10은 3,000문항을 1회, 다른 LLM 질문은 3회 반복했다. LIMIT 숫자는 1~10으로 다양화했다.
학습 중 이름 교체 40%, LLM 질문의 유의어 교체 50%를 적용했다.

전처리기는 질문의 도메인 단어·집계 표현·약어·비교 기호를 바꾼다.
숫자·날짜·DB에 있는 이름과 상품명·따옴표 안 문자열·명시적인 LIKE 검색 조각은 보호한다.
추론에는 약 44KB의 사전과 작은 Python 코드만 필요하며 NLTK나 LLM을 실행하지 않는다.

## 8. 평가 방식과 한계

기본 평가 8세트 17,676문항과 사람 말투 LLM 평가 1,000문항에서 전처리 전후를 비교했다.
입력 질문만 바꾸고 모델·정답·채점 규칙은 유지했다. SQL 실행 결과의 일치율은 보조 지표로 사용한다.

각 모델은 seed 0 한 번의 학습 결과이며, 평가셋은 개발 과정에서 확인한 세트다.
따라서 전처리 포함 점수는 **현재 시스템의 개발 평가 성능**으로 보고한다. 새로운 질문에서의 성능은 별도 평가가 필요하다.
현재 기본 실행 단계는 3단계이며, 전처리는 선택 옵션이다.
기본 배포 모델은 `models/stage3/`의 15.7M이다. 이전 단계는 `--stage 1` 또는 `--stage 2`로 선택한다.

## 부록 C. 실험 요약

수치는 EM(%)다. 초기 27M과 후속 보강 실험은 학습 조건이 달라 참고용으로 비교한다.
모델 크기의 효과는 같은 최신 데이터로 학습한 5.8M·15.7M 비교에서 확인했다.

### C-1. 날짜 조건·정렬 학습 (10-14)

날짜를 새로 넣었을 때 조건 비교와 최신순 정렬을 배울 수 있는지 확인했다.
집계 없이 일반 조회 12만 쌍으로 15M 모델을 처음부터 학습했다.
일반 기본 99.35%, 구조 변형 85.55%, 표현 변형 70.90%로 날짜 복사보다 표현 변화에 약했다.

### C-2. 집계·서브쿼리를 포함한 초기 27M 학습 (10-15)

날짜 기준선에서 집계·그룹화·서브쿼리까지 학습 범위를 넓혔다.
조합기 24만 쌍과 LLM 5천 쌍으로 27M을 10 epoch 학습해 검증 EM 93.10%를 얻었다.
이름·LIKE 복사와 새 표현의 성능이 낮아 데이터 분포와 평가 정책을 추가 점검했다.

### C-3. 보조 정렬 때문에 생긴 오답 분리 (10-15)

초기 27M의 낮은 점수 중 실제 모델 오류와 정답 표기 정책의 차이를 구분하는 진단이다.
모델을 재학습하지 않고, 저장된 정답의 동점 보조 정렬만 기본키 ASC 정책에 맞춰 다시 비교했다.
일반 평가 오답 2,193건이 이 차이만으로 발생했다. 원래 공식 점수는 유지했다.

### C-4. 데이터 재생성 후 27M 본 학습 (10-16)

정책을 반영한 SQL·질문을 다시 만들고, 조합기 30만 쌍에 LLM 질문을 더해 27M을 15 epoch 학습했다.
고급 기본 96.80%, 구조 변형 69.50%, 표현 변형 59.80%였다.
LIKE 검색 조각을 잘못 복사하거나 서브쿼리의 안쪽·바깥 조건을 빠뜨리는 문제가 남았다.

### C-5. 5.8M의 학습 속도·메모리 시험 (10-18)

작은 모델로도 3단계 학습이 가능한지 먼저 확인하기 위해 5.8M을 1 epoch만 학습했다.
데이터·토크나이저는 유지하고 검증 배치를 32로 제한해 메모리 사용을 줄였다.
검증 표본 EM 94.45%를 확인한 뒤, 별도 무작위 초기화로 15 epoch 본 학습을 진행했다.

### C-6. 초기 5.8M과 기존 27M 비교 (10-18)

고정 학습·검증 분할에서 5.8M을 15 epoch 학습하고 기존 27M과 같은 평가셋으로 비교했다.
고급 표현은 5.8M 50.55%, 27M 60.75%였고, 일반 조회·구조 성능은 대체로 비슷했다.
기존 27M에는 학습 중 옵티마이저 재시작 이력이 있어 차이를 모델 크기만의 효과로 보지는 않았다.

### C-7. 추가 보강과 LIKE 조각 분포 변경 (10-18)

숫자·집계 의도·불필요한 조건 억제 보강 8천 쌍과, 출력·비교·정렬·LIKE 방향을 구별하는 대비 7,500쌍을 추가했다.
LIKE 검색 조각도 흔한 단일 토큰·희귀 단일 토큰·다중 토큰 후보를 고르게 뽑도록 바꾸고 5.8M을 재학습했다.
고급 표현은 50.55→55.40%로 올랐지만 HAVING+LIMIT 정답은 198→44개로 줄어, 설정 묶음의 회귀를 확인했다.

### C-8. 숫자 보강 비중·검증 분할 재조정 (10-18)

HAVING+LIMIT에서 SQL을 일찍 끝내는 문제를 확인한 뒤, 숫자를 다양화하고 숫자 보강 반복을 3회에서 1회로 줄였다.
검증과 연결된 보강 205쌍도 제외하고 기존 분할·LIKE 방식·학습량으로 맞춰 5.8M을 다시 학습했다.
HAVING+LIMIT 정답은 44→244개, 고급 구조는 70.30→86.90%로 회복했지만 여러 변경의 개별 효과는 분리하지 않았다.

### C-9. 최신 데이터에서 5.8M·15.7M 크기 비교 (10-18)

C-8의 데이터·분할·토크나이저·학습량을 유지하고, 모델 구조만 15.7M으로 키워 처음부터 학습했다.
고급 구조는 86.90→97.10%로 올랐지만 고급 표현은 52.77→52.07%였다.
같은 조건에서도 크기 확대는 구조 조합에 도움이 됐고, 낯선 표현 문제는 남았다.

### C-10. 낯선 표현만 바꿔 본 원인 진단 (10-18)

고급 표현 실패가 SQL 구조보다 어휘 차이에서 오는지 확인하기 위해, 모델을 고정하고 입력의 일부 표현만 수동 치환했다.
예를 들어 `articles→items`, `record count→row count`로 바꾸자 5.8M은 52.77→80.02%가 됐다.
이는 전처리 구현 전의 원인 진단이며, 기존 원문 점수나 이후 자동 전처리 점수와 구분한다.

### C-11. 사람 말투를 반영한 LLM 질문 평가 (10-18)

2단계 사람 질문의 특징을 참고해 같은 SQL 200개를 검색형·조건 먼저 쓰기·어색한 영어·기호형·일반형으로 작성했다.
기존 두 모델을 재학습 없이 1,000문항에 평가한 결과는 5.8M 69.00%, 15.7M 69.90%였다.
전체 크기 차이는 작았고, 기호·약어와 서브쿼리에서 약점이 드러났다.

### C-12. WordNet을 이용한 학습 문항 생성 시범 (10-18)

WordNet 표현으로 학습 질문을 다양화할 수 있는지 보려고, 학습 SQL 30개에 다섯 표현 방식으로 질문 150개를 만들었다.
일반 표현 30개는 비교용으로, 동의어·약어·어순을 바꾼 120개는 보강 후보로 검수했다.
기존 학습에 넣거나 재학습하지 않았으므로, 이 실험은 생성·검수 가능성을 확인한 결과다.

### C-13. WordNet 단어 치환 전처리 (10-18)

질문에서 학습에 없던 단어를 찾아 WordNet 관계가 가까운 학습 단어로 바꾸고, 기존 모델에 넣었다.
같은 뜻의 단어만 허용하는 방식과 관계를 두 단계까지 따라가는 방식을 비교해, 후자는 고급 표현 64.28%/67.81%를 얻었다.
다만 `articles→holding`, `transactions→return`처럼 문맥에 맞지 않는 치환이 발견됐다. 수치는 5.8M/15.7M 순서다.

### C-14. 도메인 명사·구문·기호 전처리 비교 (10-18)

단어 뜻을 상품·고객·주문 도메인으로 제한하고 `avg qty→average quantity` 같은 구문·약어 규칙을 추가했다.
모델은 고정한 채 명사만·구문만·두 처리 결합·비교 기호 추가의 네 설정을 비교했다.
최종 고급 표현은 78.10%/76.08%, 사람 말투는 73.30%/73.50%로 개선됐다. 수치는 5.8M/15.7M 순서다.

### C-15. 같은 전처리의 2단계 적용 (10-18)

C-14 전처리를 그대로 쓰는 경우와 어휘·DB 보호 목록만 2단계에 맞춘 경우를, 기존 15M 세 모델에 적용했다.
재학습 없이 평가셋 14개를 비교했으며, 맞춤 버전도 사람 작성 73.33→73.00%, Gemini+GPT 합산 87.23→87.32%였다.
2단계에는 추가 이득이 작고 기존 정답이 틀리는 경우도 있어 기본 적용은 하지 않았다.

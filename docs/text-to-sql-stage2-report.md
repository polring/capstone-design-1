# Text-to-SQL 2단계 진행 보고서

최종 갱신: 2026-10-14

2단계 범위는 테이블 하나에서 WHERE 조건 0~3개(AND, 서로 다른 컬럼의 OR — 섞지 않음), 같은 컬럼 값 나열 `IN`,
비교 연산자·`BETWEEN`·이름 `LIKE`, ORDER BY, LIMIT이다. DB와 미등장 값은 1단계 것을 그대로 쓴다. 본문은 결과(1절), 남은 오답의
원인(2절), 실험에서 얻은 결론(3절), 다음 할 일(4절), 계획과 달라진 점(5절)이고, 그 뒤에 SQL 생성(6절), 학습 데이터(7절), 평가셋과
채점 규칙(8절)을 두었다. 실험 세부·설정·진행 내역은 부록에 있다. 라벨 규칙은 [라벨 규칙 문서](text-to-sql-label-rules.md)(2단계는 L6~L17),
실행 방법은 [SETUP](SETUP.md) 5~8절에 있다.

## 요약

SQL 생성기 → 질문 조합기 + LLM 학습 질문 → 학습 → 평가까지 2단계 파이프라인이 동작한다. 최종 15M 모델(`stage2_llm3`, seed 3개 평균)은
조합기 문장 평가에서 처음 보는 SQL 99.5%, 처음 보는 구조 조합 94.4%, 처음 보는 이름·ID 98.2%를 맞히고, 다른 LLM이 쓴 질문
(Gemini + GPT)은 87.2%를 맞혀 **게이트 주 목표(≥ 80%)를 넘었고 회귀 방지 줄도 지켰다**(1절). 1단계 분포 내만 seed 하나가 목표 아래인 경계다.

학습 데이터의 중심은 질문 조합기다. 생성기가 만든 SQL의 구조에서 문장을 조립하므로 라벨이 처음부터 라벨 규칙대로 붙는다.
조합기 틀로 따라잡기 어려운 말투는 외부 LLM(Claude, Gemini, GPT)이 학습 SQL에 쓴 질문 6,943쌍으로 더했다. 그중 1,490쌍은 영어 검색창을
쓰는 한국인 사용자 문체(키워드 나열, 오타, 기호)다(7절).

게이트 평가셋은 학습 질문과 같은 플랫폼으로 만든 "익숙한 말투"이고, 봉인 세트는 없다. 사람 작성 100문항은 73.3%지만, 한국인 사용자
문체·와일드카드 LIKE를 이 세트의 오답을 보고 더했으므로 이제 개발 세트에 가깝다. 남은 가장 큰 약점은 **사람 말투**(SELECT 컬럼,
부정·부등호, 키워드 나열의 AND / OR)와 **긴 SQL의 연산자**다(2절).

## 1. 게이트 결과

+ 1단계 쌍 22,361 + LLM 학습 질문 6,943쌍이고, LLM 쌍은 3번 넣고 epoch마다 유사어 교체를 한다(7절). 제약 디코더는 적용하지 않았다.

## 2. 남은 오답의 원인

| 원인 | 근거 |
| --- | --- |
| **사람 말투** | 사람 작성 오답 26개(seed 0): SELECT 12, 부등호·부정 6, 조건 컬럼 5, AND / OR 3. seed 3개가 모두 틀린 17문항은 라벨이 규칙과 다른 문항 6, 부정·부등호 뒤집힘 4("excluded" → `=`, "not in the category of" → `=`, "greater or equal" → `<=`), 키워드 나열의 and를 OR로 읽음 3, 따옴표 없는 짧은 LIKE 조각이나 조건 하나를 빠뜨림 3("contain tpu", "ends with cam"), SELECT 1("first 5 customers" → `*`)이다 |
| **긴 SQL의 조건·연산자** | GPT 구조 홀드아웃 오답 98개(seed 0): 조건 컬럼 37, 부등호 30, LIMIT 13. 조건 3개 + IN 60%, ORDER BY + LIMIT 1 65%, 조건 1개 + LIKE(정렬 붙음) 20%로 가장 약하다 |
| **LIKE × ORDER BY** | 구조 조합 중 seed 간 흔들림이 가장 크다: 조합기 문장 75.0 / 86.5 / 94.8%, GPT 60 / 64 / 76%. 오답은 대부분 LIKE 조건을 통째로 빼는 것이다. 조합기 와일드카드 비율을 33%로 두면 42%까지 무너진다(A-9) |
| **값 복사** | 이름·LIKE 조각을 비슷한 다른 문자열로 쓴다("'eiv'" → `'%drv%'`, "'mp'" → `'%car%'`, "'ens'" → 특수 토큰 `<bos>`). 틀과 무관하게 난다 |
| 사람 작성 라벨 | 작성자 C의 7문항은 "which items" → 식별 컬럼으로 L3와 반대다. 규칙대로 답하면 오답이라 규칙 일치 EM에서 뺀다 |

측정의 한계도 있다. 외부 말투 평가셋은 모두 학습 질문과 같은 플랫폼이고, Claude 미등장 값 세트는 오답을 보고 조합기를 고친 dev라 게이트에
쓰지 않는다. 사람 작성 100문항은 신뢰구간이 넓고, 한국인 사용자 문체·와일드카드를 이 세트 오답을 보고 더했으므로 일반화 근거로 약하다.

## 3. 실험에서 얻은 결론

세부 결과는 부록 A에 있다.

- **말투는 LLM 학습 질문이 가장 효과적이다.** 학습 쌍의 4%(5,453쌍)를 3번 반복 + 유사어 교체로 넣자 Claude 외부 말투 분포 내 54.6 → 77.9%,
  구조 38.3 → 68.9%, 학습에 쓰지 않은 사람 작성 54.7 → 67.7%로 올랐다(A-7). 조합기 틀을 외부 말투 오답에 맞춰 고치는 것은 보강에 쓰지 않은
  세트를 4~7%p만 올렸다(A-6). 한국인 사용자 문체 1,490쌍을 더하면 Claude 분포 내가 77.9 → 84.6%로 더 오른다(A-9, A-10).
- **조합기에 새 표기를 넣을 때는 비율을 낮게 둔다.** LIKE 문장의 33%를 와일드카드 표기("name like jo\*")로 바꾸자 따옴표 LIKE 문장이 32% 줄고,
  학습에 없는 LIKE × ORDER BY에서 LIKE 조건을 빼는 오답이 늘어 조합기 구조 홀드아웃이 회귀 줄 아래로 내려갔다(seed 하나는 42%). 10%로
  낮추자 회귀는 사라지고 와일드카드 질문은 계속 맞힌다(A-9). 표기 자체보다 기존 표현의 몫이 줄어드는 것이 문제다.
- **LLM 질문을 조합기 표현 사전으로 늘리지 않는다.** 유사어 교체는 자연스럽지만, 조건·정렬 표현 교체는 30문장 중 약 12문장의 문법을 깨고
  LLM이 쓴 새 표현을 덮어 쓴다.
- **IN 값은 질문에 나온 순서로 쓴다(L8).** 값 순서(알파벳순) 라벨은 처음 보는 이름을 정렬해야 해서 이름 3개 나열이 1%로 무너진다. 26M 모델도
  배우지 못했다(A-4).
- **이름 교체는 SQL의 모든 이름 자리를 바꿔야 한다.** 첫 이름만 바꾸면 나머지는 외운다. 전부 바꾸면 이름 나열 미등장 값이 91~93%다(A-2, A-3).
- **값 복사 자리는 문제가 아니다.** 값을 태그로 바꿔 학습하면 태그 자리만 틀린 오답은 평가마다 0~5개다. 남는 것은 문자열 복사다(A-1).
- **학습 문장 수는 병목이 아니다.** SQL당 조합기 문장을 3배로 늘려도 분포 내·처음 보는 표현은 그대로다(A-1). SQL당 3문장을 쓴다.
- **구조 홀드아웃 조합은 칸이 학습에 남는 것만 고른다.** 칸 자체를 빼면 구조가 아니라 처음 보는 표현을 잰다(A-1). 정렬이 붙은 SQL 종류를
  학습에 늘리면 처음 보는 조합도 오른다(A-5).
- **15 epoch로 학습한다.** 30 epoch는 구조 홀드아웃을 4%p 더 올리지만 학습 시간이 두 배다(A-5).
- **설정 비교는 seed 여러 개로 한다.** 조합기 문장은 seed 간 2%p 안이지만, 외부 말투는 LLM 질문이 없을 때 4~9%p 흔들린다(A-6).

## 6. SQL 생성

### 6-1. 문법

| 컬럼 종류 | 컬럼 | 연산자 | ORDER BY |
|---|---|---|---|
| ID | customer_id, item_id, order_id | `=`, `IN` | ✗ |
| 이름 | name, item_name | `=`, `IN`, `LIKE` (`'x%'` / `'%x'` / `'%x%'`) | ✗ |
| 범주형 | city, membership, category, status | `=`, `!=`, `IN` | ✗ |
| 숫자 | price, stock, quantity | `=`, `<`, `>`, `<=`, `>=`, `BETWEEN` (stock, quantity는 `IN`도) | ✓ |

- 조건 0~3개. 0개는 ORDER BY가 있을 때만이다("the 3 most expensive items"). `IN`은 조건 하나로 센다.
- 같은 컬럼의 값 나열은 `IN`(값 2~3개)이다. price에는 IN을 쓰지 않는다.
- AND와 OR는 섞지 않고, 둘 다 서로 다른 컬럼의 조건만 잇는다. IN은 조건 하나라 AND·OR와 함께 쓸 수 있다:
  `membership IN ('gold', 'platinum') AND city = 'seattle'`, `category IN ('kitchen', 'sports') OR price < 10.00`.
- OR는 ID·이름 `=`·IN 조건을 잇지 않고(LIKE는 됨), 항에 `!=`를 쓰지 않으며, LIMIT을 붙이지 않는다. LIMIT 없는 ORDER BY는 된다.
- 같은 컬럼의 범위는 `BETWEEN`으로만 쓴다. 유일 키(PK, name, item_name)의 `=`·IN 조건은 단독으로만 쓴다.
- SELECT가 `=` 조건 컬럼이면 존재 확인(L1)이다. 조건 1개, 정렬 없음일 때만 쓴다. IN 컬럼은 SELECT하지 않는다.
- LIMIT은 ORDER BY가 있을 때만 쓴다. 정렬 전 결과가 2행 미만이거나 LIMIT 이하인 SQL은 버린다.
- 정규형: AND·OR 조건은 스키마 컬럼 순서, IN 값은 값 순서, ASC 항상 표기, price는 `50.00`처럼 소수 둘째 자리.
  학습 쌍의 IN 값만 질문에 나온 순서다(L8).
- price 범위 조건 리터럴의 절반은 정수 어림수(20, 50, 100…)다. stock과 숫자 구간이 겹쳐 소수점 유무로 컬럼을 맞힐 수 없게 했다.

### 6-2. 생성 절차와 분할

`src/data/stage2/sql_gen.py` → `data/stage2/sql/`.

1. **커버리지 하한**: (테이블, 컬럼, 연산자) 칸마다 일정 수를 먼저 채운다.
2. **목표 분포**: 조건 수 0/1/2/3 = 5/35/40/20, orders 가중치 1.6. IN을 쓸 수 있는 조건의 10%(유일 키는 50%)를 IN으로, 조건 2개 이상의
   4%를 서로 다른 컬럼 OR로 만든다. 정렬은 약 29%, 그중 약 80%에 LIMIT.
3. **하한**: `stock = 0`(out of stock)과 `stock > 0`(in stock)을 포함한 SQL 각 1,000개, 존재 확인(L1) SQL 1,000개 이상. 무작위로는 존재
   확인이 0.9%뿐이다.
4. **상한**(학습 + 분포 내 평가): ID 조건 포함 30%, 결과 0행 10%, 1단계 모양(조건 1개 `=`, 정렬 없음) 5%.
5. **분할**: 학습 / 분포 내 평가는 SQL 단위로 나눈다. 구조 홀드아웃과 미등장 값은 아래처럼 따로 만든다.
6. **1단계와 겹침 금지**: 1단계 평가 SQL은 2단계 학습·분포 내 평가에 넣지 않고, 1단계 학습 SQL은 2단계 평가에 넣지 않는다.
   1단계 학습 쌍을 2단계 학습에 섞고 1단계 평가셋도 계속 재기 때문이다.

**구조 홀드아웃 조합**: 조건 3개 × LIMIT, LIKE × ORDER BY, LIKE × BETWEEN, LIKE × `!=`(items), BETWEEN × `!=`. 사용자가 드물게 쓰는
조합만 골랐다(개발용 사용자 말투 100문장에 0번). 이 조합에 걸리는 SQL은 학습에 넣지 않지만, 조합의 각 요소와 모든 칸은 학습에 있다.
자주 쓰는 조합(OR × ORDER BY, orders의 `!=`·BETWEEN, `!=` × 숫자 비교 등)은 학습에 둔다.

**미등장 값 모양**: `holdout.json` 리터럴을 `=` 또는 IN 조건 하나에 넣고, 리터럴마다 들어갈 수 있는 모양을 전부 하나씩 만든다. 유일 키는
단독 / IN 2개 / IN 3개, orders의 FK는 여기에 AND 2·3개, 정렬, 정렬 + LIMIT까지다. 나머지 조건에는 IN을 쓰지 않고, 결과 0행과 구조
홀드아웃 조합은 피해 값 복사만 잰다.

| 분할 | SQL | 골격 종류 | ID 포함 | 0행 | 1단계 모양 |
|---|---|---|---|---|---|
| train | 40,000 | 5,311 | 28.3% | 10.0% | 5.1% |
| indist | 2,000 | 1,114 | 26.8% | 11.0% | 2.5% |

조건 0개가 목표보다 적은 것은 WHERE 없는 고유 SQL이 수백 개뿐이기 때문이다.

### 7-1. 질문 조합기

SQL 레코드의 구조 필드(조건, 연결어, 정렬, LIMIT)를 받아 질문 한 문장을 만든다(`src/data/stage2/compose.py`, `data/stage2/composer/`).
LLM이 문장을 쓰지 않으므로 라벨이 처음부터 규칙대로 붙는다.

| 구성 | 내용 |
| --- | --- |
| 문장 틀 (`frames.json`) | SELECT 역할별 문형 274개(eval 전용 36). star, ident, own_id, exists, attr(컬럼별) |
| 표현 사전 (`lexicon.json`) | (SQL 조각, 위치) → 같은 뜻의 표현. 조건 키 48개·정렬 키 6개에 표현 696개(eval 전용 117) |
| 유사어 사전 (`synonyms.json`) | 틀 문장의 일상 단어를 50% 확률로 대체어로 바꾼다(give me → get me, list → display 등 27개 키). 역할·컬럼·연산자 단서는 바꾸지 않는다 |
| 값 | 리터럴을 그대로 복사. price는 20 / 20.00 / $20 / 20 dollars·bucks. LIKE 표현의 10%는 와일드카드 표기다(`--wildcard-ratio`, "where name like jo\*", "with name %ed%", "whose names are \*ro\*") |
| 평가 전용 표현 | `split: eval` 표시. 학습 문장에는 나오지 않고, 처음 보는 표현 평가(phrase)만 쓴다 |
| 검사 (`compose check`) | 모든 SQL이 문장이 되는지, 값 복사, 사전 충돌, eval 표현 누출, 결정성, 라벨 규칙 판정(0.1% 초과면 실패) |

- 틀의 출처는 세 가지다. 1단계 LLM 학습 질문의 문형(79개), 틀·규칙을 모르는 LLM 세션 4개가 쓴 사용자 말투 100문장(`data_raw/stage2/user_style/`:
  "top 5 most expensive items", "order 5312 status?", "electronics under 50 bucks", "…, lowest stock first, just 10"), 외부 말투 dev(Claude 미등장 값)
  오답(값 나열 연결 and·쉼표·슬래시·공백, `!=` 표현 anything but·skipping, 단수 LIMIT "the single cheapest", 속성을 뒤에서 묻는 어순)이다.
  dev 오답으로 고쳤으므로 그 dev 점수는 일반화 근거로 쓰지 않는다.
- SQL 하나로 만들 수 있는 문장은 중앙값 1,743개(train, 최소 50)다. 같은 SQL을 epoch 3번 조합하면 평균 2.99개의 서로 다른 문장이 나온다.

### 7-2. LLM 학습 질문

외부 LLM이 **학습 SQL**에 대한 질문을 쓰고 정답은 생성기의 SQL을 그대로 쓴다(`question_gen --split train`). 평가 SQL로 만든 질문은 학습에
넣지 않는다(`to-train`이 막는다). 배치(SQL 25개)마다 독립 세션이 쓰고, 라운드마다 표본을 읽어 라벨과 질문이 맞는 것을 확인했다.

| 라운드 | 플랫폼 | 학습 SQL | 검증 통과 | 버린 것 |
| --- | --- | --- | --- | --- |
| `llm_r1` | Claude (페르소나 plain, spoken, command, context, shorthand) | 200 | 976 / 1,000 | 라벨 규칙 22, 중복 2 |
| `llm_r2` | Claude | 100 | 499 / 500 | 라벨 규칙 1 |
| `llm_r3` | Gemini 3.7 Flash (배포 묶음) | 426 | 1,997 / 2,005 | 라벨 규칙 8 |
| `llm_r3` | GPT (배포 묶음) | 424 | 1,981 / 1,995 | 라벨 규칙 14 |
| `llm_r4` | Claude (한국인 사용자 문체 v1) | 100 | 499 / 500 | 값 누락 1 |
| `llm_r5` | Claude (한국인 사용자 문체 v2) | 200 | 991 / 1,000 | 라벨 규칙 8, 값 누락 1 |

- **배포 묶음**(`make-handout`): 다른 플랫폼을 쓰는 팀원에게 SQL 목록과 안내문(스키마, 질문 요건, 라벨 규칙을 뜻 단위로 적은 표)만 보낸다.
  팀원의 LLM이 생성 프롬프트를 직접 쓰고 파일럿 25개로 고친 뒤 배치마다 질문 5개씩 받는다. 학습 SQL과 평가 SQL을 섞어 보내 받는 쪽은
  어느 것이 평가용인지 모른다.
- **학습 방법**: 학습 쌍의 약 4%라 `--llm-repeat 3`으로 3번 넣고, epoch마다 유사어 사전으로 문장 일부를 바꾼다(확률 0.5, `synonym_swap.py`,
  이름 교체 전). 학습 전에 질문을 소문자로 바꾼다.
- 플랫폼마다 말투가 다르다. Gemini는 SQL당 5문장이 서로 비슷하고 컬럼 이름을 그대로 쓴다("category is …" 28%). GPT는 한 세션이 모두 써서
  질문 자리마다 첫머리가 굳었지만("I need / I'd like" 71%), 학습에 없는 단어가 든 문장이 17%로 표현은 가장 다양하다.
- **한국인 사용자 문체**(`llm_r4`·`llm_r5`): LLM은 따로 지시하지 않으면 다듬은 문장만 써서(A-8) 따로 만들었다. 프롬프트
  (`data_raw/stage2/prompt_korean_users_v2.txt`)는 영어 검색창을 쓰는 한국인 사용자 5명이 키워드 나열, 한국어식 어순, 오타, SQL 줄임말로 쓰게 하고, 5개 중 1개쯤은 평범한 질문형으로 쓰게 한다. `llm_r5`는 물음표 20%(사람 작성 23%), 비교 조건을 기호(`>`, `>=`)로 쓴
  문장 20%(19%), 학습에 없는 단어(대부분 컬럼 이름 오타: pirce, stcok, cateogry) 28%(16%)다. 값(이름, LIKE 조각, 범주값)에는 오타가 없다.

### 7-3. 2단계 이름 교체

`src/data/stage2/name_swap.py`. 2단계로 학습하면 epoch마다 이름 조건 쌍의 40%에 적용한다. SQL을 파싱해 이름 컬럼의
`=`·IN·LIKE 조건을 **전부** 바꾼다.

- `=`·IN 이름은 값마다 다른 가짜 이름으로, SQL의 같은 자리에서 바꾸고 다시 정렬하지 않는다(질문 순서 유지, L8).
- LIKE 조각은 같은 방향·같은 길이의 가짜 조각으로 바꾼다. 바꿀 값은 질문에 정확히 한 번 나와야 한다.
- `stage2_llm3` 학습 데이터에서 epoch마다 약 13,200쌍이 바뀐다.

## 8. 평가셋과 채점 규칙

### 8-1. 평가셋

`data/stage2/eval/pairs.json` + `sql.json` 하나에 담고 쌍마다 `set`을 적는다. `python -m src.data.stage2.eval_build`로 만들고 손으로 고치지
않는다. 모든 평가 SQL은 학습 SQL에 없다.

| 평가셋 | 쌍 | 만든 방법 | 쓰임 |
| --- | --- | --- | --- |
| indist / struct / holdout | 2,000 / 2,000 / 2,049 | 분포 내 / 구조 홀드아웃 / 미등장 값 SQL마다 조합기 문장 하나 (학습과 다른 seed) | 회귀 방지 |
| phrase | 2,000 | indist SQL에 eval 전용 표현을 한 자리(틀 / 조건 / 정렬)에만 넣은 조합기 문장 | 회귀 방지 |
| `ext_r1_<분할>_claude` | 595 / 494 / 486 | Claude, 평가 SQL 320개 × 페르소나 5개 | 참고. 미등장 값(holdout)은 dev |
| `ext_r2_<분할>_gemini` | 180 / 209 / 105 | Gemini, 배포 묶음의 평가 SQL 99개 | 게이트 |
| `ext_r3_<분할>_gpt` | 399 / 398 / 189 | GPT(gpt-5.5, Codex CLI), 평가 SQL 200개를 배치마다 새 세션으로 | 게이트 |
| human | 100 | 팀원 4명이 SQL 25개씩 보고 직접 씀 (분포 내 15, 구조 5, 미등장 값 5) | 참고 |

- 외부 말투(계획서 3-4 방식 A)는 SQL을 주고 질문을 받는다. Claude 페르소나는 검색창 키워드, 소문자·오타 채팅, 비원어민, 장황한 설명, 업무
  메시지다. 프롬프트에는 스키마, 값 표기, SQL의 뜻만 넣고 조합기 틀·학습 문장은 넣지 않는다. 검증에서 값 누락·SQL 키워드·라벨 규칙 위반을
  뺀다(라운드별 0.2~2.8%, 대부분 라벨 규칙).
- Gemini·GPT 평가 SQL은 Claude 평가 SQL에서 뽑아 같은 SQL로 플랫폼을 비교할 수 있다.
- Claude·Gemini·GPT 모두 학습 질문을 쓴 플랫폼이라 **봉인 세트가 아니다.**
- 사람 작성 문항은 SQL과 맞는지 하나씩 확인해 값 오타, 밑줄 컬럼 이름, 숫자 단어 LIMIT 같은 것은 말투를 살려 고쳤다. 라벨 규칙과 어긋난
  문항은 고치지 않고 규칙 일치 EM이 뺀다.

### 8-2. 채점 규칙

`src/data/stage2/sql_rules.py`. `python -m src.run --stage 2 --model <체크포인트> --evaluation`이 쓴다.

- **EM**: 정규형(`sql_ast.canonical`)으로 비교한다. IN 값 순서와 AND·OR 조건 순서는 무시하고, 리터럴 표기는 정규형과 같아야 한다.
- **다중 정답 EM**: 정답이 `*` 또는 식별 컬럼이고 질문에 어느 쪽 단서도 없으면 다른 쪽도 정답으로 본다.
- **규칙 일치 EM**: 라벨이 라벨 규칙과 어긋난 문항(`drop_reason`)을 뺀다.
- **오답 분류**: table, select, where_col, op, literal, conn, order, limit, malformed. 분할·페르소나·작성자·구조 조합·미등장 값 모양·조건·
  정렬별로 따로 집계한다.

### 8-3. 게이트 목표

외부 말투 결과를 보기 전에 정한 목표다(1절 표의 "목표" 열). seed 3개 평균으로 판정하고 가장 낮은 seed 점수를 함께 적는다. 결과를 보고
바꾸지 않으며, 바꿔야 하면 한 번만 사유와 함께 바꾼다. 주 목표를 넘고 회귀 방지 줄을 지키면 3단계로 넘어간다.

- 주 목표는 Gemini + GPT 합산이다. Claude 외부 말투와 사람 작성은 참고 목표로 둔다. Claude 미등장 값은 dev라 뺐고, 사람 작성은 신뢰구간이
  ±10%p라 게이트에 쓰지 않는다.
- 게이트 평가셋 문장에서는 조합기 틀을 뽑지 않는다(게이트가 dev가 된다).

## 부록 A. 실험 상세

| 실행 | 데이터 | 부록 |

### A-1. 태그 복사 실험

조합기 문장의 이름·ID·LIKE 조각·숫자를 태그(`val1`, `val2`, …)로 바꿔, 값 복사 없이 SQL 구조와 값 자리를 맞히는지 봤다. 5M 모델,
학습 step 수를 같게 맞춰 SQL당 문장 3개(10 epoch)와 1개(30 epoch)를 비교했다(`experiments/stage2/tagged/`).

| 평가 (각 2,000쌍) | SQL당 문장 3개 | 문장 1개 |
| --- | --- | --- |
| indist | 100% | 100% |
| struct | 55.4% | 46.6% |
| phrase (eval 자리 하나만 eval 표현) | 71.8% | 72.1% |

- 태그 자리만 틀린 오답이 평가마다 0~5개라, 값을 어느 자리에 쓰는지는 문제가 아니다.
- 문장을 3배로 늘려도 indist·phrase는 그대로이고, struct는 조합별로 반대 방향으로 크게 움직였다(OR × ORDER BY +54%p, `!=` × orders −48%p).
  BETWEEN × orders와 `!=` × orders는 그 칸 자체가 학습에 없어 구조보다 처음 보는 표현을 쟀다.
- phrase 0%인 표현은 모두 학습에 없는 단어를 담는다("got any …", "north of $…"). 아는 단어를 새로 조합한 표현은 맞힌다.

### A-2. 첫 2단계 학습 (파일럿)

조합기 문장 120,000 + 1단계 쌍 22,484로 처음 학습했다(`stage2_pilot`, 검증 EM 99.3%). 조합기 문장 indist 100%, holdout 95.5%, struct 40.5%였다.

- holdout 오답은 대부분 **OR로 묶은 이름의 두 번째 이후**를 자르거나 바꾼 것이다("keith" → "ke"). 1단계 이름 교체가 첫 이름만 바꿔서
  나머지 이름은 학습 내내 DB 실제 이름이라 외운다. 그래서 2단계 이름 교체(7-3)를 만들었다.
- 사용자 말투 100문장: 문법 안 89개 중 81개(91%). 오답은 따옴표 없는 짧은 LIKE 조각을 `=`로 씀(3), LIMIT 없는 정렬에 `LIMIT 1`을 붙임(3),
  orders의 `!=`를 본 적 없음(1)이었고 모두 조합기에 반영했다.

### A-3. 2단계 이름 교체 학습

### A-4. OR 값 순서 실험

사용자는 "vest or radio"처럼 아무 순서로 나열한다. 조합기가 값을 섞어 나열하게 하고 학습 SQL의 값 순서를 두 가지로 해 봤다.

| 평가 | 값 순서 라벨 15M | 값 순서 라벨 26M | **질문 순서 라벨 15M (채택)** |
| --- | --- | --- | --- |
| 검증 EM | 95.7% | 92.8% | 99.5% |
| holdout 이름 1개 / OR 2개 / OR 3개 | 46 / 6 / 1% | 79 / 24 / 3% | 92 / 92 / 87% |
| indist 전체 | 95.6% | 94.3% | 99.9% |

값 순서 라벨은 처음 보는 이름을 알파벳순으로 놓아야 해서 이름 복사가 무너지고, 모델을 키워도 풀리지 않았다.

| --- | --- | --- |
| struct 전체 | 93.4% | 97.5% |

### A-9. 한국인 사용자 문체·와일드카드 (`stage2_llm2`)

`stage2_llm1` 설정에 한국인 사용자 문체 질문 `llm_r4`·`llm_r5`(1,490쌍)를 더하고(LLM 학습 질문 6,943쌍), 조합기 LIKE 문장의 3분의 1을
와일드카드 표기로 바꿔 BPE부터 다시 학습했다(데이터 `runs/stage2/llm2_data/`). seed 3개 평균, 괄호는 `stage2_llm1` 대비.

| 평가 | seed 0 / 1 / 2 | 평균 |
| --- | --- | --- |
| Gemini + GPT 합산 | 88.4 / 85.9 / 89.9% | 88.1% (+1.3) |
| └ 분포 내 · 미등장 값 · 구조 홀드아웃 | | 94.5 · 93.0 · 79.5% (+2.6 · +2.7 · −0.6) |
| 조합기 문장: 분포 내 · 미등장 값 · 처음 보는 표현 | | 99.6 · 99.0 · 88.8% (+0.2 · +1.6 · +0.6) |
| **조합기 문장: 구조 홀드아웃** | **87.8 / 85.2 / 96.2%** | **89.8% (−4.2), 목표 90% 미달** |
| Claude 분포 내 · 구조 · 미등장 값 | | 85.8 · 70.6 · 90.1% (+7.9 · +1.7 · +4.3) |
| 사람 작성 | 72 / 74 / 75% | 73.7% (+6.0), 규칙 일치 79.2% (+6.5) |
| 1단계 분포 내 (규칙 일치) · 미등장 값 | | 96.6 · 92.8% (+0.6 · +1.1) |

- **조합기 구조 홀드아웃 하락은 LIKE 조건 누락이다.** seed 0·1 오답 243·295개 중 198·243개가 gold의 LIKE를 빼먹었다("starts with p",
  "ending in et"처럼 와일드카드 없이 쓴 조각, 주로 `!=`·ORDER BY와 함께). seed 2는 17개로 `llm1`(28~81개)보다 적어 seed 간 차이가 크다.
  Gemini 구조 홀드아웃이 3.2%p 내린 것도 같은 칸이다. SQL이 ORDER BY·LIMIT 앞에서 끊기는 오답(seed마다 약 20개)은 `llm1`과 비슷하다.
- **사람 작성** 문항별(seed 3개 중 2개 이상 정답): 새로 맞힘 8, 새로 틀림 2. 와일드카드 7문항은 0 → 4개. 와일드카드 추가는 사람 작성 오답을
  보고 정했으므로 이 세트는 이제 개발 세트에 가깝다.
- **LIKE 누락 원인은 와일드카드 조합기다.** `llm2`에서 조합기 문장만 `llm1`의 것(와일드카드 이전, LIKE 문장 5,696개만 다름)으로 되돌린
  `stage2_llm2_nowild`(seed 0, 토크나이저는 `llm2`)는 조합기 구조 홀드아웃 93.7%(LIKE × ORDER BY 79.0%, `llm2` seed 0 53.2%, `llm1` 77.0%)로
  회귀 줄을 넘는다. LIKE 오답은 질문 표기(따옴표 / 맨 단어)와 상관없이 ORDER BY와 함께일 때만 늘었다. 다른 평가는 `llm2`와 비슷하다:
  Gemini + GPT 88.3%, Claude 분포 내 86.6%, 1단계 분포 내 97.1%. 사람 작성은 71%로, 와일드카드 7문항은 1개만 맞힌다(`llm2` 4개).
- **와일드카드 비율 10%면 둘 다 잡는다.** 조합기 LIKE 표현에서 와일드카드를 고를 확률을 0.1로 둔 데이터(`compose build --wildcard-ratio 0.1`,
  LIKE 문장의 10.2%, LIKE 아닌 문장은 `llm2`와 같음)로 학습한 `stage2_wild10_s1`(seed 1, `llm2`가 가장 크게 무너진 seed) 결과, 괄호는
  `llm1` / `llm2` seed 1: 조합기 구조 홀드아웃 96.2%(94.8 / 85.2), LIKE × ORDER BY 94.0%(84.0 / 42.0), Gemini + GPT 89.1%(86.3 / 85.9),
  Claude 분포 내 85.4%(78.3 / 86.4), 사람 작성 76%(68 / 74), 와일드카드 7문항 5개(0 / 4). 1단계 분포 내는 95.7%(96.8 / 96.5)로 목표 96%
  아래다.
- 실행 결과는 `runs/stage2/stage2_llm2{,_s1,_s2}/`, `stage2_llm2_nowild/`, `stage2_wild10_s1/`. 데이터 사본은 `runs/stage2/llm1_data/`(와일드카드
  없음), `llm2_data/`(33%), `wild10_data/`(10%, 조합기 문장만)에 있다.

# AGENTS.md

Guidance for coding agents in this repository. Keep only rules and traps here; progress, numbers, and
how-to live in `docs/` (Korean). When work changes progress or numbers, update that stage's report (the
plan holds only design and completion criteria), not this file.

From-scratch Text-to-SQL Transformer (4-person capstone): English question → SQLite SQL. Stage 1 scope:
single table, `SELECT` one column or `*`, single `WHERE` equality. Stage 2: 0–3 `WHERE` conditions
(AND, or OR across columns — never mixed), same-column value lists as `IN`, comparisons, `BETWEEN`, name `LIKE`,
`ORDER BY`, `LIMIT`. Stage 3 adds dates, aggregates, GROUP BY/HAVING and depth-one non-correlated scalar
subqueries. Stage 3 is the default runtime; its report records current results and limitations.

## Scratch-build constraint (critical)

Model, tokenizer, training loop, and inference are implemented from scratch — that is the point of the
project.

| | Allowed | Forbidden |
|---|---|---|
| Libraries | Python stdlib, PyTorch (tensor ops/autograd/optimizer only), SQLite, NumPy, TensorBoard | HuggingFace `tokenizers`/`transformers`, SentencePiece, tiktoken, any off-the-shelf model/tokenizer |
| Weights | Random init only | Pretrained checkpoints |
| Data | DB/SQL generated by code; questions by an external LLM; some eval questions hand-written | An LLM generating or modifying ground-truth SQL |
| Reference | nanoGPT may be read and rewritten | — |

## Data layout and paths

All paths live in `src/config.py` and follow `STAGE` (`config.stage_paths(N)` for another stage). `STAGE` defaults to 3;
select stages explicitly with `--stage N` in train/run/BPE/DB generation; demo follows `TEXT_TO_SQL_STAGE`.
Scripts under `src/data/stage<N>/` pin their own
stage's paths (`stage_paths(N)`), never `config.STAGE` — otherwise a stage-1 script would write into stage-3 data. Tests run
as stage 1 (`tests/conftest.py`).
Runtime DB paths are `data/stage<N>/db/`. The stage-2 DB has the same bytes as stage 1;
its SQL generator still defaults to `data/stage1/db/`. Stage 3 uses its expanded date DB. Every command
takes its input files and output location as arguments and falls back to these defaults — don't hardcode paths.
Roles come from **folder position**, not names:

- `data/stage<N>/train/*.json` and `*.json.gz` — **every** JSON here is training data and BPE corpus. Never put eval pairs here.
  Stage 3 uses the frozen validation file `data/stage3/validation/pairs.json` by default; train never splits it again.
- Eval sets are `pairs.json` + `sql.json` (metadata of the SQL used, incl. `holdout_tier`), never written by hand; loading
  fails if a pair's SQL is missing from `sql.json`. Stage 1: one folder per set, `data/stage1/eval/<name>/` (build `sql.json`
  with `python -m src.run --build-sql <name> --sql <sql file>`; `holdout_qwen` is the old Qwen-written set, comparison only).
  Stage 2: one combined `data/stage2/eval/pairs.json` + `sql.json`, each pair tagged `set` (`src/evaluation/eval_sets.py`
  splits by it, so sets are still scored separately). Rebuilt with `python -m src.data.stage2.eval_build [composer|ext|human]`,
  which replaces only those sets (pairs keep `sql_group`, the canonical SQL that keys `sql.json`); to add teammates' human
  questions, fill `data_raw/stage2/human/sql_list_<writer>.json` and re-run.
- Stage 3 also uses one combined `data/stage3/eval/pairs.json` + `sql.json`; all 14 sets, including external
  questions, are tagged with `set`. `eval/external_sources.json` records external sources.
- `data/stage<N>/tokenizer/seed_tokens.json` — seed IDs are `260 + list order`: reordering or inserting changes
  every token ID, so retrain BPE and the model after editing. `tokenizer.json` is the trained result (seeds + merges).
- `models/stage<N>/` — the one committed release (`model.pt` + the `tokenizer.json` it was trained with +
  `model_info.json`), made by `python -m src.release`. Never write eval/prediction outputs here; they go to `runs/`.
- `data_raw/`, `runs/`, `experiments/` — uncommitted. `experiments/stage1/` holds the pre-stage-2 experiments
  (regularization/EMA, pointer tokens, ensemble, new-style eval, Qwen3-14B question pilot); their results live only in the stage-1 report.
  Question-generation rounds are validated in `data_raw/` and moved by hand.
- Stage-specific code lives in `src/data/stage<N>/` (SQL/question generation, label cleaning, name swap,
  scoring rules `sql_rules.py`); `src/evaluation/scoring.py` keeps only stage-independent scoring.
  Stage-2/3 schema helpers live in each `schema.py`, LIKE interpretation in `sql_ast.py`, name augmentation
  in `name_swap.py`, and synonym augmentation in `compose.py`; no shared modules exist for these four roles.

## Design decisions that are easy to undo by accident

- **Loss on SQL tokens only** (`loss_mask`); the question is given at inference.
- **Right padding without an attention mask is correct** for this causal decoder. Batched generation must
  group prompts of equal length (`generate_batch` in `src/inference/generate.py`).
- **`FFN_DIM = round(8d/3)`**: SwiGLU has 3 matrices, so this matches the plan's parameter budget
  (GELU 4d, 2 matrices). Don't revert to `3d`/`4d`.
- **Validation split is by SQL, not by pair**, and `eval_indist` is never used for checkpoint selection —
  otherwise scores measure memorization.
- **Holdout literals** (`data/stage<N>/db/holdout.json`) must never appear in training SQL (`db_gen.load_bans()`).
- **Stage-2 SQL never overlaps stage-1 data the wrong way**: stage-1 eval SQL stays out of stage-2 train/indist, and
  stage-1 train SQL stays out of every stage-2 eval split (`src/data/stage2/sql_gen.py`, checked by `verify`). Stage-1
  train pairs are mixed into stage-2 training and stage-1 eval sets keep being scored, so both rules are load-bearing.
- BPE seed tokens (SQL keywords, columns, categorical values) stay single tokens; merge ties break
  deterministically.
- Text values lowercase, SQL keywords uppercase.
- **One question, one SQL**: labels follow the label rules — L1–L17 for stages 1–2 and L18–L29 for stage 3 in [docs/text-to-sql-label-rules.md](docs/text-to-sql-label-rules.md)
  (plan 4-5 holds only the principle). Training data is cleaned with
  `python -m src.data.stage1.clean_ambiguous --apply` (re-run after adding pairs; rebuild BPE after). Stage 2 uses
  `src/data/stage2/clean_ambiguous.drop_reason`: `compose build` drops stage-1 pairs that violate it, `compose check`
  fails if composer sentences disagree with it, `question_gen validate` drops external eval items that violate it. Eval sets are
  left as-is for comparability. `sql_rules.select_ambiguous` is a frozen metric rule — don't edit it to match
  the label rules.
- **Rule-consistent EM** (`rule_consistent` in eval results) drops eval items whose gold label violates the label
  rules, using the same `clean_ambiguous.drop_reason` (via `sql_rules.label_mismatch`). Stage-1 in-dist is gated on
  it. Never tune those rules by looking at eval failures — change them only from training data, then re-clean.

## LLM question generation rules

- One independent LLM session per batch — a session handling a whole round converges on stock phrasings.
- Don't let the generating session write a generator script; read real sentences, since `validate()` and
  `template_check()` can be gamed (a 0% repeat ratio is a reason to inspect, not a pass).
- Keep the checker's internals out of the generating session's context.
- Local models (Qwen3-14B) ignore rule 10 (existence-check framing when `select == where_col`); filter
  with `soft_flags()`.
- After merging new pairs, run `python -m src.data.stage1.question_gen corpus-check` and remove both sides of
  any label conflict.
- Stage 2 (`src/data/stage2/question_gen.py`): external-eval rounds (`data_raw/stage2/ext_*`) are built from eval SQL and
  never go into training (holdout literals, eval SQL). Training questions come from `--split train` rounds with the
  training personas; `to-train` refuses eval rounds. Keep a sealed external eval from a different platform than training.

## Commands

Run from the repo root with `.venv\Scripts\python` (paths are cwd-relative). Full list: SETUP.md.

```
python -m pytest tests/ -v          # unit tests
python -m src.train --overfit 100   # pipeline sanity check: must reach EM 100%
python -m src.train                 # full training (name swap 40% per epoch) + final eval -> runs/stage<N>/ffn<D>_swap40/
python -m src.release --ckpt runs/stage<N>/<run>/best.pt   # -> models/stage<N>/ (the committed release)
python -m src.run --evaluation      # score the release on every eval set (--model / --eval-sets to change)
python -m src.run --input "..."     # question -> SQL -> shop.db result (no --input: interactive)
python -m src.demo all              # follow one example through every stage, input -> output
```

`src/` root holds only `config.py` and the commands above (`python -m src.<name>`); libraries live in subpackages —
`src/inference/` (loading, generate) and `src/evaluation/` (scoring, eval_sets) have no command line.
